A value whose name suggests it holds a secret (a password, an API key, a token, ...) should not be passed to a logging call.

Why is this an issue?

Log output routinely ends up somewhere that isn't as tightly access-controlled as the application itself - a log aggregator, a support ticket, a developer's terminal, a file shipped to a third-party monitoring service. Once a secret is written to a log, it is effectively out of the application's control: it can't be rotated away from those copies, and anyone with read access to the logs can use it directly.

_logger.LogInformation("User authenticated with {Password}", password);

Exceptions

Only calls to Microsoft.Extensions.Logging.ILogger (LogTrace/LogDebug/LogInformation/ LogWarning/LogError/LogCritical) and Serilog (Log.* / ILogger.*) are checked. For each argument, only its own name - or, for the message template, the name of each {Placeholder} - is inspected; the rule does not trace where the value itself originally came from.

How to fix it

Remove the secret from the log call entirely, or replace it with a non-reversible indicator (for example whether a value was present, or its length) if that is genuinely useful for diagnostics.

Code examples

Noncompliant code example

_logger.LogInformation("User authenticated with {Password}", password); // Noncompliant {{Do not log 'Password' - its name suggests it holds a secret.}}

Compliant solution

_logger.LogInformation("User {UserId} authenticated", userId);
