ASP.NET GET and HEAD actions should not bind parameters from the request body.

Why is this an issue?

HTTP does not define generally applicable request-body semantics for GET or HEAD. Clients, proxies, caches, and servers can reject or ignore such a body, so an action that requires it is not reliably callable across the HTTP ecosystem.

How to fix it

Move search or filter values into route or query parameters. If the operation requires a structured request body, expose it through a method such as POST whose request content has defined semantics.

Code examples

Noncompliant code example

[HttpGet]
public IActionResult Search([FromBody] SearchRequest request) => // Noncompliant {{Remove '[FromBody]' from this GET action; request-body semantics are not defined for this HTTP method.}}
    Ok(_search.Find(request));

Compliant solution

[HttpGet]
public IActionResult Search([FromQuery] SearchRequest request) =>
    Ok(_search.Find(request));

Exceptions

The rule reports only an explicit ASP.NET FromBodyAttribute. It does not infer binding sources from parameter complexity and deliberately does not cover DELETE, whose request-content handling varies between API conventions.

For Minimal APIs, the rule covers parameters of inline handlers registered with the official MapGet extension and official MapMethods registrations whose directly supplied array initializer has a complete element equal to GET or HEAD. Constants nested inside conditional or other compound expressions are not treated as method-list elements. Named handlers, nested lambdas, indirect method lists and lookalike attributes or mapping APIs are outside this scope.
