Controllers should receive application identity through a dedicated identity provider or a Juno [FromToken] UserContext, and should express claim requirements through authorization policies.

Why is this an issue?

Reading or inspecting ClaimsPrincipal in controller code couples the HTTP boundary to token layout and claim names. It spreads authentication details across actions and private helpers, makes authorization behavior harder to audit, and makes claim-schema changes unnecessarily risky.

This rule reports direct use of claims lookup and inspection APIs in types derived from ASP.NET Core ControllerBase. Passing the principal to IAuthorizationService.AuthorizeAsync remains valid because the policy, rather than the controller, performs the authorization decision.

How to fix it

Move identity extraction to an application identity provider, inject the resulting application identity into the controller, or bind Juno UserContext with [FromToken]. Define claim-based access requirements in an authorization policy and evaluate that policy through ASP.NET Core authorization.

Code examples

Noncompliant code example

public IActionResult Get()
{
    var userId = User.FindFirstValue(ClaimTypes.NameIdentifier); // Noncompliant
    return Ok(userId);
}

Compliant solution

public IActionResult Get([FromToken] UserContext user)
{
    return Ok(user.UserId);
}
