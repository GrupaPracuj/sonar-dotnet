Committing to the database and then publishing a message, with no outbox, writes to two systems that cannot fail together.

Why is this an issue?

The commit and the publish are two independent writes with no transaction spanning them. Whatever happens between them decides the outcome, and one of the outcomes is silent divergence:

  • the commit succeeds, then the broker is unreachable, the process is recycled, or the pod is evicted - the data changed and nobody was told. No error is raised anywhere, because the request already succeeded;
  • the publish is retried by a framework that does not know the commit already happened - consumers see the event twice.

The first case is the dangerous one. There is no failed request to investigate, no exception in the log, and no way to detect it from either side - the producer's data is correct and the consumer simply never heard. It surfaces days later as two services disagreeing, and the only repair is a manual reconciliation.

public async Task Accept(Order order, CancellationToken cancellationToken)
{
    _context.Orders.Add(order);
    await _context.SaveChangesAsync(cancellationToken);   // write 1: committed

    await _publisher.Publish(new OrderAccepted(order.PublicId), cancellationToken); // write 2: may never happen
}

An outbox removes the second write. The message is stored in the same transaction as the data, so both land or neither does, and a separate process delivers it afterwards with at-least-once semantics.

Exceptions

A publish that happens before the commit is not reported here. That is a different defect - it holds the transaction open across a network call - and it is not what this rule looks for: only a publish that follows a commit in the same method is reported.

Set the outboxTypes parameter to the types that mark an approved outbox - a company wrapper, a MassTransit outbox marker interface, a base class - and a method inside such a type is not reported. The parameter defaults to empty, so out of the box every commit-then-publish pair is reported.

The rule reads one method body and does not follow calls, so a commit and a publish split across two methods are not reported. An issue here is reliable; the absence of one is not proof that the flow is safe.

How to fix it

Store the message in the same transaction as the data and let a delivery process publish it - the MassTransit Entity Framework outbox, or the approved company outbox. If an outbox genuinely does not apply, make the consumer side idempotent and reconcile explicitly, and record that decision.

Code examples

Noncompliant code example

public async Task Accept(Order order, CancellationToken cancellationToken)
{
    _context.Orders.Add(order);
    await _context.SaveChangesAsync(cancellationToken);

    await _publisher.Publish(new OrderAccepted(order.PublicId), cancellationToken); // Noncompliant {{This publish follows a database commit with no outbox - if it fails, the data has changed and nobody was told.}}
}

Compliant solution

// The outbox stores the message in the same transaction as the data; delivery happens afterwards.
public async Task Accept(Order order, CancellationToken cancellationToken)
{
    _context.Orders.Add(order);
    await _outbox.Publish(new OrderAccepted(order.PublicId), cancellationToken);
    await _context.SaveChangesAsync(cancellationToken);
}
