A for loop should not capture its own control variable in a lambda or anonymous method that is added to a collection, scheduled to run later, or subscribed to an event.

Why is this an issue?

A lambda captures variables by reference, not by value. When a lambda created inside a for loop captures the loop's own control variable, every lambda created across every iteration shares the exact same variable. If the lambda does not run immediately - it is stored, scheduled, or subscribed instead - it only runs after the loop has already finished mutating that variable, so every deferred call sees whatever value the variable ended up with, typically the value that made the loop condition false.

var tasks = new List<Action>();
for (int i = 0; i < 10; i++)
{
    tasks.Add(() => Use(i)); // every task added here calls Use(10), never Use(0), Use(1), ...
}

foreach is not affected by this rule: since C# 5, the compiler creates a fresh iteration variable for every pass through a foreach loop, so each lambda captures its own distinct copy. A hand-written for or while loop gets no such help - the loop variable is one single variable for the entire loop, mutated in place by the loop's own increment/condition.

How to fix it

Copy the loop variable to a new local variable declared inside the loop body, before the lambda is created, and capture that copy instead. Because the copy is a fresh variable on every iteration, each lambda captures a different one.

Code examples

Noncompliant code example

var tasks = new List<Action>();
for (int i = 0; i < 10; i++)
{
    tasks.Add(() => Use(i)); // Noncompliant {{'i' is captured by reference and mutated by this loop - every deferred use of this lambda will see the SAME final value, not the value at each iteration. Copy it to a local variable inside the loop body first.}}
}

Compliant solution

var tasks = new List<Action>();
for (int i = 0; i < 10; i++)
{
    var iCopy = i;
    tasks.Add(() => Use(iCopy));
}

Exceptions

Only lambdas passed to a fixed list of recognizable "runs later" sinks are reported: an argument to a method named Add, Enqueue or Push; an argument to Task.Run, Task.Factory.StartNew, ContinueWith or ThreadPool.QueueUserWorkItem; an argument to the Thread constructor; or the right-hand side of a += event subscription. A lambda that is consumed synchronously within the same statement - for example fully enumerated by a LINQ chain that runs before the next iteration - is not reported, since the loop variable it captures still has the value from the current iteration when the lambda actually runs.
