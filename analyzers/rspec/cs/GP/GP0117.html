Why is this an issue?

Dapper maps a result set to an object by name. A column in a SELECT that does not exist in the table makes the query fail, but a column that exists in neither the table nor the mapped type does something quieter: nothing. And when the SQL and the DTO agree on a name that the table does not have, the property is simply never populated - it keeps its default, and no exception is raised anywhere.

Nothing in the C# compiler or in Dapper checks a column name, so such a name can only be caught by comparing it against another statement that touches the same table. If a project writes a table with INSERT and reads it back with SELECT, the two column lists are two independent spellings of one schema - and a name that appears on only one side is a typo, a rename that was applied in one place, or a column that no longer exists.

This rule reports a column read from a table that no statement in the project ever writes to that table.

What is the potential impact?

Silently unpopulated fields. A value read into a default - null, 0, 0001-01-01 - travels on into audit records, responses and messages without any failure to point at the cause.

Exceptions

To keep this from reporting on tables the project only partly owns, no issue is raised when:

  • the project writes fewer than three columns of the table, so its INSERT is not a usable picture of the schema;
  • half or more of the SELECT list is unaccounted for, which means the table is read far more widely than it is written rather than misspelled;
  • the column is a conventional database-generated one - a surrogate key, a concurrency token, or an audit stamp such as RowCreatedAtUtc - since those are produced by the database or by a migration and are legitimately never written by application SQL.

SELECTs with a join or a union are not analysed at all, because a column cannot be attributed to one table from the text alone.

How to fix it

Check the reported name against the migration that created the table, then correct whichever side is wrong. When the column was renamed, make sure the DTO property is renamed with it - a DTO that still matches the old spelling is what let the mismatch go unnoticed.

Noncompliant code example

// The INSERT writes AppName and ExecutedAtUtc ...
private const string Insert = @"
INSERT INTO dbo.AllocatedProductsExpirations
(AllocationId, Type, FundsJson, RequestId, AppName, RequestingUser, JwtClient, ExecutedAtUtc, WalletId) VALUES
(@AllocationId, @Type, @FundsJson, @RequestId, @AppName, @RequestingUser, @JwtClient, @ExecutedAtUtc, @WalletId)";

// ... but the SELECT asks for AppDane and ExpirationDateUtc, which the table does not have.
private const string Select = @"
SELECT WalletId, AllocationId, Type, ExpirationDateUtc, FundsJson, RequestId, AppDane, JwtClient, RequestingUser
FROM dbo.AllocatedProductsExpirations
WHERE AllocationId = @AllocationId;"; // Noncompliant: 'ExpirationDateUtc' and 'AppDane' are never written

Compliant solution

private const string Select = @"
SELECT WalletId, AllocationId, Type, ExecutedAtUtc, FundsJson, RequestId, AppName, JwtClient, RequestingUser
FROM dbo.AllocatedProductsExpirations
WHERE AllocationId = @AllocationId;";
