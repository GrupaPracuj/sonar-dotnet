Collection queries serving synchronous request-response APIs should put an explicit upper bound on the number of rows returned.

Why is this an issue?

An unbounded result set makes endpoint latency, memory usage and response size depend on database growth. A query that is safe today can become an outage after the table accumulates enough rows.

The rule follows calls within one compilation from MVC actions and inline Minimal API handlers. It reports only cases it can prove: constant-text Dapper collection queries without TOP, LIMIT or FETCH FIRST/NEXT, and direct Entity Framework Core collection materialization rooted in a DbSet without Take. Dynamic SQL, stored procedures, unknown query helpers and calls through another project are ignored rather than guessed.

How to fix it

Add pagination or another explicit business limit. The bound may be supplied as a parameter; it does not need to be a hard-coded number.

Code examples

Noncompliant code example

const string Sql = "SELECT Id, Name FROM dbo.Items ORDER BY Id";
return await connection.QueryAsync<Item>(new CommandDefinition(Sql, cancellationToken: cancellationToken)); // Noncompliant

Compliant solution

const string Sql = """
    SELECT Id, Name
    FROM dbo.Items
    ORDER BY Id
    OFFSET @Offset ROWS FETCH NEXT @Limit ROWS ONLY
    """;
return await connection.QueryAsync<Item>(
    new CommandDefinition(Sql, new { request.Offset, request.Limit }, cancellationToken: cancellationToken));
