HTTP actions should declare the concrete schema of error response bodies.

Why is this an issue?

Declaring only an error status such as 400 tells OpenAPI clients that the response exists, but not how to deserialize its body. When an action explicitly returns BadRequest(error), NotFound(error) or another error factory with a value, its matching response metadata should include that value's concrete type.

The rule examines only response factories returned directly by controller actions. It reports a status only when that status is already documented without a concrete type, leaving missing statuses to GP0100 and avoiding duplicate findings.

Exceptions

Bodyless errors, actions excluded from API Explorer, actions covered by ASP.NET API conventions, and classic MVC controllers serving views are not reported. Responses produced indirectly by middleware, filters or called services are not inferred.

How to fix it

Add the error model type to the matching ProducesResponseType or equivalent response attribute.

Code examples

Noncompliant code example

[HttpPost]
[ProducesResponseType(StatusCodes.Status400BadRequest)]
public IActionResult Create(Request request) // Noncompliant
{
    return BadRequest(new ErrorResponse("Invalid request"));
}

Compliant solution

[HttpPost]
[ProducesResponseType(typeof(ErrorResponse), StatusCodes.Status400BadRequest)]
public IActionResult Create(Request request)
{
    return BadRequest(new ErrorResponse("Invalid request"));
}
