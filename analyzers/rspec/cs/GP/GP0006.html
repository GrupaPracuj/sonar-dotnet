An access-control decision should not be based directly on an identity claim such as sub, name, email, phone, phone_number, preferred_username, upn, given_name, family_name or unique_name.

Why is this an issue?

Identity claims describe who the caller is, not what the caller is allowed to do. Branching authorization logic on the presence or value of an identity claim conflates authentication data with permission data: it bypasses whatever role/permission/policy model the application uses elsewhere, and it silently breaks if that claim's format or presence changes (for example when the identity provider changes, or a service account with no email claim calls the endpoint). Access decisions should be based on dedicated authorization claims or policies instead.

public bool HasAccess(User user) =>
    user.HasClaim("sub");

Besides the generic HasClaim overloads, the rule also covers the GP.Juno claim helpers that each imply one fixed claim type (HasUserClaim, FindUserClaim, HasApplicationClaim, HasUserGroupClaim and friends). Those are matched only when the method actually comes from a GP.Juno namespace, so an unrelated method that happens to share the name is not reported. Claim types written as ClaimTypes.Email are recognised whether the class is imported or fully qualified.

HasCompanyClaim/FindCompanyClaim are intentionally not covered: in this organization, the "company" claim is an accepted authorization dimension (for example, gating access to company-scoped resources on a multi-tenant platform) rather than an identity leak.

The complete set of recognized ClaimTypes members is NameIdentifier, Name, Email, MobilePhone, Upn, GivenName and Surname.

How to fix it

Base the decision on a dedicated permission/role claim or an explicit authorization policy instead of an identity claim.

Code examples

Noncompliant code example

public bool HasAccess(User user) =>
    user.HasClaim("sub"); // Noncompliant {{Do not base access control on identity claim 'sub'.}}

Compliant solution

public bool HasAccess(User user) =>
    user.HasClaim("filestore_access");
