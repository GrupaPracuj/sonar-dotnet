An access-control decision should not be based on the value of an identity claim such as sub, name, email, phone, phone_number, preferred_username, upn, given_name, family_name or unique_name.

Why is this an issue?

Identity claims describe who the caller is, not what the caller is allowed to do. Branching authorization logic on a specific identity claim value - a hardcoded subject id, a specific email address, a specific username - conflates authentication data with permission data: it bypasses whatever role/permission/policy model the application uses elsewhere, hardcodes an exception for one particular person, and silently breaks if that claim's format changes (for example when the identity provider changes).

public bool HasAccess(User user) =>
    user.FindFirst("sub").Value == "a3f1c9d2-...";

Merely checking whether an identity claim is present - HasClaim("sub"), FindFirst("sub") != null, an Option<Claim>.HasValue check, or a predicate that only matches on Type - is not reported. Presence alone does not tie the decision to a specific identity; only reading and comparing the claim's actual Value does.

How to fix it

Base the decision on a dedicated permission/role claim or an explicit authorization policy instead of a specific identity value.

Code examples

Noncompliant code example

public bool HasAccess(User user) =>
    user.FindFirst("sub").Value == "a3f1c9d2-..."; // Noncompliant {{Do not base access control on identity claim 'sub'.}}

Compliant solution

public bool HasAccess(User user) =>
    user.HasClaim("filestore_access");

Recognized shapes

Besides the generic HasClaim(Func<Claim, bool>)/FindFirst/FindAll overloads, the rule also covers the GP.Juno claim helpers that each imply one fixed claim type (FindUserClaim, FindApplicationClaim, FindUserGroupClaim and friends) when the caller reads their result's Value. The parameterless Has*Claim() helpers (HasUserClaim, HasApplicationClaim, HasUserGroupClaim) return a bool and are always pure existence checks, so they are never reported. Every Juno match requires the method to actually come from a GP.Juno namespace, so an unrelated method that happens to share the name is not reported. Claim types written as ClaimTypes.Email are recognised whether the class is imported or fully qualified.

HasCompanyClaim/FindCompanyClaim are intentionally not covered at all, existence or value: in this organization, the "company" claim is an accepted authorization dimension (for example, gating access to company-scoped resources on a multi-tenant platform) rather than an identity leak.

The complete set of recognized ClaimTypes members is NameIdentifier, Name, Email, MobilePhone, Upn, GivenName and Surname.

Exceptions

[Authorize(Policy = "sub")]-style policy names are always reported when the policy name matches one of the recognized identity claims, since the attribute alone gives no way to tell whether the policy itself only checks presence or also checks value.
