A collection on a contract should be a materialized read-only collection, not a lazy or queryable sequence.

Why is this an issue?

IEnumerable<T> promises nothing about when its items are produced. On a contract that matters, because the serializer is what ends up enumerating it - so whatever work backs the sequence runs during serialization, outside the code that built the message and outside its error handling. If the sequence was a LINQ query over a DbContext, the database is queried at that point; if the scope has already been disposed, the publish fails with an exception that points at the serializer rather than at the cause.

IQueryable<T> is the same problem with a provider attached, and IAsyncEnumerable<T> cannot be serialized synchronously at all. All three also hide whether the sequence can be enumerated twice, which serializers and retries both do.

A materialized read-only collection removes the question: the items exist, the count is known, and enumerating it again is free and identical.

public sealed class OrderAcceptedContract
{
    public IEnumerable<OrderLine> Lines { get; init; }
}

Exceptions

IReadOnlyCollection<T>, IReadOnlyList<T>, arrays and concrete collections are not reported. Mutable collection types are outside this rule's scope - it is about when the items materialize, not about who can change them.

How to fix it

Declare the property as IReadOnlyList<T> or IReadOnlyCollection<T> and materialize the sequence when the message is built.

Code examples

Noncompliant code example

public sealed class OrderAcceptedContract
{
    public IEnumerable<OrderLine> Lines { get; init; } // Noncompliant {{'Lines' is a lazy sequence - the serializer would enumerate it; use IReadOnlyList.}}
}

Compliant solution

public sealed class OrderAcceptedContract
{
    public IReadOnlyList<OrderLine> Lines { get; init; }
}
