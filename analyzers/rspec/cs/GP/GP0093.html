An exception filter should not contain an explicit throw expression.

Why is this an issue?

When an exception filter throws, the CLR catches that exception and treats the filter as if it returned false. The new exception is silently lost, making the behavior difficult to distinguish from an intentional rejection by the filter.

How to fix it

Make the filter return a boolean without throwing. Move work that can fail into the catch body or execute it before entering the guarded operation.

Code examples

Noncompliant code example

catch (Exception) when (canHandle ? true : throw new InvalidOperationException()) // Noncompliant {{Remove this throw from the exception filter; the CLR silently treats the filter as false when it throws.}}
{
}

Compliant solution

catch (Exception) when (canHandle)
{
}

Exceptions

A throw inside a lambda declared in a filter is not reported because the lambda can be evaluated later, outside filter execution.
