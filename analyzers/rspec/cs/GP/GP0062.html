A message contract should stay small enough to be understood and versioned.

Why is this an issue?

Contract size is a coupling measure. Every property is something a consumer may come to depend on and the producer can therefore no longer change, so a contract with sixty fields is sixty commitments to services you do not control. Large contracts also tend to be the symptom rather than the disease: the producer stopped deciding what the event means and started sending its whole model, which is how the contract ends up mirroring a database table.

Depth compounds it. Each nested level multiplies what a consumer has to deserialize and match, and a deep graph is where breaking changes hide - a rename four levels down is invisible in review and fatal at runtime.

public sealed record OrderAccepted(
    Guid OrderId,
    Customer Customer,       // which nests Address, which nests Country...
    /* ... 40 more properties ... */);

Exceptions

All three limits are rule parameters: maxProperties (default 30), maxDepth (default 4) and maxComplexTypes (default 10). The count is of the contract's own public data members; depth follows contract-like types only and stops at BCL types, so a string or a DateTimeOffset is never a level.

How to fix it

Split the contract along the events that actually happened, or send identifiers and let the consumer fetch what it needs.

Code examples

Noncompliant code example

public sealed class OrderAcceptedContract // Noncompliant {{'OrderAcceptedContract' exceeds a message contract limit: 34 properties, above the limit of 30.}}
{
    // 34 properties
}

Compliant solution

public sealed record OrderAcceptedContract(Guid OrderId, string CustomerReference, decimal Total, string Currency, DateTimeOffset OccurredAt);
