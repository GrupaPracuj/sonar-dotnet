Code with an injected TimeProvider should use it consistently instead of reading a static clock.

Why is this an issue?

An injected clock makes time deterministic in tests and keeps one operation on one time source. Reading TimeProvider.System, DateTime.Now, DateTime.UtcNow or their DateTimeOffset equivalents bypasses that abstraction. Tests that freeze the injected clock then still produce real timestamps, and one operation can observe inconsistent times.

The rule reports only when the containing type already has a System.TimeProvider field, property, or primary-constructor parameter. Clock implementations and types named *TimeProvider or *Clock are excluded because they need a system time source.

How to fix it

Read time through the available provider, for example with GetUtcNow().

Noncompliant code example

public sealed class ReservationConsumer(TimeProvider timeProvider)
{
    public AuditTrace CreateTrace() =>
        new(DateTimeOffset.UtcNow); // Noncompliant
}

Compliant solution

public sealed class ReservationConsumer(TimeProvider timeProvider)
{
    public AuditTrace CreateTrace() =>
        new(timeProvider.GetUtcNow());
}
