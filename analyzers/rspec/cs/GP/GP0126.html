A synchronous request-response API path should not execute a separate database operation for every loop element.

Why is this an issue?

Database calls in a loop create N+1 round trips and make endpoint latency grow with input size. They also consume connection-pool capacity for the entire request and can amplify a small request into a large database load.

The rule reports Dapper, Entity Framework Core and Juno IDbExecute operations whose arguments directly depend on a variable declared by the loop. Retry and polling loops whose query does not vary per iteration are not reported.

Such a call qualifies in one of two ways. Either it is reachable, within one compilation, from an MVC action or an inline Minimal API handler - calls through another project are deliberately not guessed - or the loop iterates the result of another query or request made in the same method. That second form is the N+1 shape itself, so it is reported wherever it sits, including data access that lives in its own assembly, away from the endpoint that ends up paying for it.

A loop whose element is itself a collection is not reported either: one query per batch - from Chunk, from GroupBy or from a hand-rolled batcher yielding List<T> - is the remedy this rule steers towards, not the defect. A query nested one loop deeper, inside the batch, is still reported.

How to fix it

Collect the identifiers and issue one set-based query, use an appropriate bulk operation, or load the required data before entering the loop.

Code examples

Noncompliant code example

foreach (var id in request.Ids)
{
    results.Add(await connection.QuerySingleAsync<Item>(
        new CommandDefinition(SqlById, new { id }, cancellationToken: cancellationToken))); // Noncompliant
}

Compliant solution

var results = await connection.QueryAsync<Item>(
    new CommandDefinition(SqlByIds, new { request.Ids }, cancellationToken: cancellationToken));
