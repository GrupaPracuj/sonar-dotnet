A contract should be declared in a nullable-enabled context, so its properties say which values are optional.

Why is this an issue?

Required versus optional is contract information, not an implementation detail. It is the difference between "this field will always be there" and "you must handle its absence", and it is the single thing a consumer most needs to know before writing code against a payload. Without nullable annotations, string Email says nothing at all: the producer may guarantee it, or may send null half the time, and the consumer finds out in production.

With annotations on, the declaration answers the question. string Email promises a value, string? Email admits it may be missing, and the compiler holds the producer to it on the way in and warns the consumer on the way out. The same information also drives generated OpenAPI schemas and serializer required-ness, so turning it on fixes the documentation and the validation at the same time.

// no #nullable enable, and no <Nullable>enable</Nullable> in the project
public sealed record CandidateRegisteredContract(Guid CandidateId, string Email, string PhoneNumber);

The rule reads the nullable context at the contract's declaration, so it accounts for both the project-level setting and a per-file #nullable enable. Only the annotation context matters - warnings can stay off.

How to fix it

Set <Nullable>enable</Nullable> for the project that holds the contracts, then mark the genuinely optional members ?. Doing it project-wide is better than per file: a contract assembly where half the types are annotated is harder to read than one where none are, because the reader cannot tell which halves mean what.

Code examples

Noncompliant code example

public sealed record CandidateRegisteredContract(Guid CandidateId, string Email); // Noncompliant {{'CandidateRegisteredContract' is declared without nullable reference types, so its members do not say which values are optional.}}

Compliant solution

#nullable enable

public sealed record CandidateRegisteredContract(Guid CandidateId, string Email, string? MiddleName);
