Why is this an issue?

A method that accepts a CancellationToken does so because the work behind it can be abandoned - a client that hung up, a request that exceeded its deadline, a host that is shutting down. Passing CancellationToken.None (or default) hard-codes the opposite: this particular call will run to completion no matter what happens around it.

The interesting case is not a single call, but where the token was supposed to come from. When the enclosing method has no CancellationToken parameter at all, CancellationToken.None is not a local decision - it is the point at which the cancellation chain is cut. Every caller above it loses the ability to stop this work, and the omission is invisible: the code compiles, the signature looks complete, and the call reads as if a token had been considered.

This is deliberately narrower than "a token is in scope but was not passed". If a token is available, forwarding it is the fix and GP0027 reports it. This rule covers the case where there is nothing to forward, so the fix is to widen the signature.

What is the potential impact?

Work continues after the caller has given up: connections and threads stay occupied past a client disconnect, request timeouts do not take effect, and shutdown waits for calls that no longer have a consumer.

Exceptions

No issue is raised where no caller could supply a token: Main, Dispose, DisposeAsync and finalizers. Lambdas and local functions are also skipped, because their signature is dictated by whatever framework invokes them.

How to fix it

Add a CancellationToken parameter to the enclosing method and pass it to the call. Then keep going up: the parameter is only useful once the callers thread a real token into it, ultimately from the request, the consume context or the host lifetime.

Noncompliant code example

public async Task<IEnumerable<Acceptance>> GetAcceptors(string jobOfferId)
{
    var sender = _senderFactory.Create(ServiceName);
    var result = await sender
        .AppendPathSegments("job-offers", jobOfferId, "acceptances")
        .Get(CancellationToken.None); // Noncompliant: nothing can ever cancel this HTTP call

    return await result.ReceiveJson<IEnumerable<Acceptance>>(CancellationToken.None); // Noncompliant
}

Compliant solution

public async Task<IEnumerable<Acceptance>> GetAcceptors(string jobOfferId, CancellationToken cancellationToken)
{
    var sender = _senderFactory.Create(ServiceName);
    var result = await sender
        .AppendPathSegments("job-offers", jobOfferId, "acceptances")
        .Get(cancellationToken);

    return await result.ReceiveJson<IEnumerable<Acceptance>>(cancellationToken);
}
