A struct should not rely on the default ValueType.Equals(object) when Equals is called, or on default equality and hashing when it is used as a dictionary/set key.

Why is this an issue?

Every struct inherits Equals(object) and GetHashCode() from System.ValueType unless it overrides them itself. The default equality compares the struct's fields by calling each field's Equals; reference-type fields therefore follow their own equality implementation and are not always compared by reference. The runtime can optimize some layouts, but the fallback may use reflection-based field inspection, and the default hash code is not designed around the type's domain identity. Relying on these defaults can add avoidable cost and can include fields that should not participate in the domain's equality or hashing semantics.

public struct OrderLine
{
    public int Quantity;
    public string ProductCode; // a reference-type field
}

var a = new OrderLine { Quantity = 1, ProductCode = "SKU-1" };
var b = new OrderLine { Quantity = 1, ProductCode = "SKU-1" };
bool same = a.Equals(b); // uses ValueType's field-wise default rather than declared OrderLine semantics

The rule reports two ways this default reaches production code:

  • .Equals() resolving to the inherited ValueType.Equals because the struct never overrode it.
  • A struct missing either an Equals or GetHashCode override used as the key type of a Dictionary<TKey, TValue> or the element type of a HashSet<T> without an explicit comparer, so lookups rely on the default equality and hashing path.

Exceptions

record struct types are never reported: the compiler synthesizes explicit, field-by-field Equals, GetHashCode, == and != for them. Plain enum types are a different TypeKind entirely and always use the built-in, fast comparison - they are not a concern here at all.

A call resolved to a typed IEquatable<T>.Equals(T) implementation is not reported. A Dictionary<TKey, TValue> or HashSet<T> constructed with a non-null explicit IEqualityComparer<T> is also not reported, because it does not rely on the struct's default comparer.

This rule also flags usage sites, not only declarations - including struct types that come from a third-party library outside your control, where adding IEquatable<T> or overriding Equals/GetHashCode yourself is not an option.

How to fix it

Override Equals(object) and GetHashCode() on the struct (and, ideally, implement IEquatable<T> and overload operator==/operator!=) so comparisons are explicit and based on the fields that actually define the struct's value. When the struct belongs to a third-party library and cannot be changed, avoid relying on its default equality: compare the fields you care about explicitly, or supply an explicit IEqualityComparer<T> to the dictionary or set instead of depending on the default one.

Code examples

Noncompliant code example

public struct OrderLine
{
    public int Quantity;
    public string ProductCode;
}

var lines = new Dictionary<OrderLine, decimal>(); // Noncompliant {{'OrderLine' is used as a Dictionary/HashSet key but does not override Equals/GetHashCode - lookups will use slow, reflection-based comparison.}}

Compliant solution

public struct OrderLine : IEquatable<OrderLine>
{
    public int Quantity;
    public string ProductCode;

    public override bool Equals(object obj) => obj is OrderLine other && Equals(other);
    public bool Equals(OrderLine other) => Quantity == other.Quantity && ProductCode == other.ProductCode;
    public override int GetHashCode() => (Quantity, ProductCode).GetHashCode();
}

var lines = new Dictionary<OrderLine, decimal>();

For a third-party struct, supply an explicit comparer:

var lines = new Dictionary<ExternalOrderLine, decimal>(new ExternalOrderLineComparer());
