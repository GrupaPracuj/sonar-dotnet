A struct that has not overridden Equals(object) (and correspondingly GetHashCode()) should not be compared, hashed, or used as a dictionary/set key based on that default behavior.

Why is this an issue?

Every struct inherits Equals(object) and GetHashCode() from System.ValueType unless it overrides them itself. ValueType's versions use reflection to enumerate and compare every field - this is slow, and for a struct that contains a reference-type field, it compares that field by reference, not by value. Two structs that clearly represent the same value can therefore compare as unequal, or end up in different hash buckets, simply because their reference-type fields happen to point at different (but equal) instances.

public struct OrderLine
{
    public int Quantity;
    public string ProductCode; // a reference-type field
}

var a = new OrderLine { Quantity = 1, ProductCode = "SKU-1" };
var b = new OrderLine { Quantity = 1, ProductCode = "SKU-1" };
bool same = a.Equals(b); // may be false: ProductCode is compared by reference, not by content

The rule reports three ways this default falls back into production code:

  • Comparing two structs with == when neither side has overloaded the operator itself - so whatever ends up running is not the fast, correct comparison the code likely intended.
  • .Equals() resolving to the inherited ValueType.Equals because the struct never overrode it.
  • A struct without an Equals/GetHashCode override used as the key type of a Dictionary<TKey, TValue> or the element type of a HashSet<T> - every lookup then pays the reflection cost and risks the reference-comparison bug above.

Exceptions

record struct types are never reported: the compiler synthesizes a correct, fast, field-by-field Equals, GetHashCode, == and != for them. Plain enum types are a different TypeKind entirely and always use the built-in, fast comparison - they are not a concern here at all.

This rule also flags usage sites, not only declarations - including struct types that come from a third-party library outside your control, where adding IEquatable<T> or overriding Equals/GetHashCode yourself is not an option.

How to fix it

Override Equals(object) and GetHashCode() on the struct (and, ideally, implement IEquatable<T> and overload operator==/operator!=) so comparisons are explicit, fast, and based on the fields that actually define the struct's value. When the struct belongs to a third-party library and cannot be changed, avoid relying on its default equality: compare the fields you care about explicitly, or supply an explicit IEqualityComparer<T> to the dictionary or set instead of depending on the default one.

Code examples

Noncompliant code example

public struct OrderLine
{
    public int Quantity;
    public string ProductCode;
}

var lines = new Dictionary<OrderLine, decimal>(); // Noncompliant {{'OrderLine' is used as a Dictionary/HashSet key but does not override Equals/GetHashCode - lookups will use slow, reflection-based comparison.}}

Compliant solution

public struct OrderLine : IEquatable<OrderLine>
{
    public int Quantity;
    public string ProductCode;

    public override bool Equals(object obj) => obj is OrderLine other && Equals(other);
    public bool Equals(OrderLine other) => Quantity == other.Quantity && ProductCode == other.ProductCode;
    public override int GetHashCode() => (Quantity, ProductCode).GetHashCode();
}

var lines = new Dictionary<OrderLine, decimal>();
