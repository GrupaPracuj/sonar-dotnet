Juno infrastructure handlers should not be assumed to inherit authorization configured later in the ASP.NET Core pipeline.

Why is this an issue?

Juno's ASP.NET integration registers handlers such as /__handlers, /dependency/assembly, /service-dependencies and /service-apis as branch middleware while UseJuno is being configured. A later UseAuthorization call does not execute for requests handled by those branches. The endpoints can therefore remain anonymous even when OpenAPI or application controllers require authentication.

The assembly endpoint exposes library names and versions, while the service endpoints reveal internal topology. This information can materially help an attacker select vulnerable dependencies or map internal services.

The rule reports only a semantically confirmed Juno UseJuno call whose callback configures ASP.NET web handlers through UseDistributedConfig or UseWebApp, when UseAuthorization is called later on the same application builder in the same execution context.

How to fix it

Protect the infrastructure paths before UseJuno with authentication-aware middleware, expose them only on an internal listener or trusted ingress, or disable handlers that are not required. Do not rely solely on moving or retaining the later UseAuthorization call: classic branch middleware has no endpoint authorization metadata for it to evaluate.

Code examples

Noncompliant code example

app.UseJuno(JunoConfig.ConfigureJuno); // Noncompliant
app.UseAuthorization();
app.MapControllers();

Compliant solution

app.UseAuthentication();
app.UseMiddleware<JunoInfrastructureAuthorizationMiddleware>();
app.UseJuno(JunoConfig.ConfigureJuno);
app.UseAuthorization();
app.MapControllers();
