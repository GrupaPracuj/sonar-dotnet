An endpoint should not put an exception's message, stack trace or type into the response.

Why is this an issue?

Exception text is written for whoever is debugging the service, and it says what they need: the SQL that failed, the path on disk, the host name, the internal type that threw, sometimes the value being processed. Returning it hands all of that to the caller. MITRE describes the weakness as:

The product generates an error message that includes sensitive information about its environment, users, or associated data.

The information is useful to an attacker precisely because it is accurate. A connection failure names the database server; a deserialization failure names internal types and namespaces; a constraint violation names tables and columns. None of that is guessable from the outside, and each response narrows down what the next probe should be. A stack trace also reveals the library versions in use, which turns a generic vulnerability advisory into a targeted one.

It is not good for the caller either. An exception message is not a contract: it changes wording between framework versions and is often localised, so a client that parses it breaks silently on an upgrade.

catch (Exception ex)
{
    return StatusCode(500, ex.Message);
}

The rule reports Message, StackTrace, Source, InnerException and ToString() on an exception, when the value reaches the response - returned from the action, or passed to a method that builds the body. Logging the same value is a different concern and is not reported: the log is where it belongs.

How to fix it

Log the exception with its detail, and return a response that carries a stable error code and nothing internal - ProblemDetails with a type and a title the client can act on. Where a correlation id is available, returning that gives support a way back to the logged exception without exposing it.

Code examples

Noncompliant code example

[HttpGet("{id}")]
public IActionResult Get(int id)
{
    try
    {
        return Ok(_orders.Find(id));
    }
    catch (Exception ex)
    {
        return StatusCode(500, ex.Message); // Noncompliant {{Do not put 'Exception.Message' in a response - return a ProblemDetails without internal details.}}
    }
}

Compliant solution

[HttpGet("{id}")]
public IActionResult Get(int id)
{
    try
    {
        return Ok(_orders.Find(id));
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Failed to read order {OrderId}", id);
        return Problem(title: "The order could not be read.", statusCode: 500);
    }
}
