Explicit HTTP error response bodies should use the standard ProblemDetails format defined by RFC 9457.

Why is this an issue?

An API that answers one error with an anonymous object, the next with a bare string and a third with its own DTO forces every client to write a separate parser for each endpoint, and to know in advance which shape a given status will carry. ProblemDetails is the one shape clients already know how to read:

HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "https://errors.example.com/invalid-order",
  "title": "The order is invalid",
  "status": 400,
  "detail": "The delivery date is in the past.",
  "orderId": "42"
}

Anything the error needs beyond the standard members - orderId above - stays allowed as an extension, so the format costs nothing in expressiveness.

ASP.NET Core already returns this format for the errors it produces itself: the automatic model-validation response of an [ApiController], the Problem() and ValidationProblem() helpers, and the AddProblemDetails() middleware. A hand-written error body means the same API reports errors in two formats, and the framework only documents one of them.

The rule looks at error responses - status 400 to 599 - returned from API controller actions and inline Minimal API handlers, and at the error types declared with ProducesResponseType on an action or on the controller. An error without a body, the Problem() and ValidationProblem() factories, and any type derived from ProblemDetails are accepted.

How to fix it

Return one of the framework factories instead of a custom body, and declare ProblemDetails as the error type. Keep exception messages and stack traces out of the members the client sees.

Code examples

Noncompliant code example

public IActionResult Create(CreateOrder order) =>
    BadRequest(new { Code = "invalid-order" }); // Noncompliant

Compliant solution

public IActionResult Create(CreateOrder order) =>
    Problem(
        type: "https://errors.example.com/invalid-order",
        title: "The order is invalid",
        statusCode: StatusCodes.Status400BadRequest);

The declared error type is checked the same way:

Noncompliant code example

[ProducesResponseType(typeof(OrderError), StatusCodes.Status400BadRequest)] // Noncompliant
public IActionResult Create(CreateOrder order) => Problem(statusCode: StatusCodes.Status400BadRequest);

Compliant solution

[ProducesResponseType(typeof(ProblemDetails), StatusCodes.Status400BadRequest)]
public IActionResult Create(CreateOrder order) => Problem(statusCode: StatusCodes.Status400BadRequest);

When a returned body and the metadata are wrong for the same status, only the returned body is reported - fixing it is what fixes the response.

When the error carries its own fields, derive from ProblemDetails rather than replacing it:

public sealed class OrderProblemDetails : ProblemDetails
{
    public string OrderId { get; init; }
}

A returned ProblemDetails whose Status contradicts the HTTP status is the subject of GP0131.
