Explicit HTTP error response bodies should use the standard ProblemDetails format defined by RFC 9457.

Why is this an issue?

Returning unrelated strings, anonymous objects and application-specific DTOs for different errors forces clients to implement a separate parser for each endpoint. ProblemDetails provides stable fields for machine-readable type, status, title and safe detail while still allowing application-specific extensions.

The rule checks explicit response factories returned from API controllers and inline Minimal API handlers, as well as concrete error schemas declared with response metadata. When a returned body and method-level metadata violate the rule for the same status, only the returned body is reported. Controller-level metadata remains a separate shared contract and is reported independently. Bodyless errors, framework Problem and ValidationProblem factories, middleware-generated responses and types derived from ProblemDetails are accepted.

How to fix it

Return Problem(), ValidationProblem(), Results.Problem(), or pass a suitable ProblemDetails subtype as the error body. Keep internal exception details out of the public fields.

Code examples

Noncompliant code example

return BadRequest(new { Code = "invalid-order" }); // Noncompliant

Compliant solution

return Problem(
    type: "https://errors.example.com/invalid-order",
    title: "The order is invalid",
    statusCode: StatusCodes.Status400BadRequest);

A returned ProblemDetails whose Status contradicts the HTTP status is the subject of GP0131.
