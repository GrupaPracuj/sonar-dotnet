Database access should preserve the connection and transaction context supplied by Juno. Two equivalent patterns are supported: an IDbExecute operation executed by Juno, or direct Dapper access on a connection created by IAdoConnectionFactory.CreateConnection().

Why is this an issue?

Constructing the connection yourself means supplying the connection string yourself, which is the actual problem: the address, credentials, failover target and pooling settings stop coming from the service's configured data source and start coming from whatever string is in scope at that point. It also bypasses the transaction accessor, so the new connection is invisible to any Juno transaction that is already open - work you believe is transactional silently is not.

public async Task<Order> Find(int id)
{
    using var connection = new SqlConnection(_connectionString);
    return await connection.QuerySingleAsync<Order>("select * from Orders where Id = @id", new { id });
}

Direct Dapper is valid when the receiver can be traced to IAdoConnectionFactory.CreateConnection(). Such calls use CommandDefinition so the caller's CancellationToken is preserved. If the method starts a transaction, every Dapper operation before its commit or rollback must receive that exact transaction, either in CommandDefinition or in Dapper's transaction argument. A transaction opened on one connection cannot be used to justify work on another connection.

The rule targets Dapper Query* and Execute* operations. Configuration and utility APIs such as SqlMapper.AddTypeHandler, AddTypeMap, PurgeQueryCache and AsTableValuedParameter do not access a database and are not reported.

Inside an IDbExecute, Dapper operations must receive the IDbTransaction parameter supplied by Juno. Omitting it can make one command escape the surrounding transaction or fail at runtime when the provider requires commands on a transactional connection to enlist explicitly. The same requirement applies when the operation uses a Dapper CommandDefinition.

How to fix it

Express the work as an IDbExecute and let Juno pass the connection and ambient transaction, or create the connection through IAdoConnectionFactory and pass the cancellation token and active transaction in every Dapper command.

Code examples

Noncompliant code example

public async Task<Order> Find(int id)
{
    using var connection = new SqlConnection(_connectionString); // Noncompliant
    return await connection.QuerySingleAsync<Order>("select * from Orders where Id = @id", new { id });
}

public async Task Save(CancellationToken token)
{
    await using var connection = connectionFactory.CreateConnection();
    await using var transaction = await connection.BeginTransactionAsync(token);
    await connection.ExecuteAsync(
        new CommandDefinition("update Orders set Saved = 1", cancellationToken: token)); // Noncompliant: transaction omitted
}

Compliant solution

public async Task Save(CancellationToken token)
{
    await using var connection = connectionFactory.CreateConnection();
    await using var transaction = await connection.BeginTransactionAsync(token);
    await connection.ExecuteAsync(
        new CommandDefinition(
            "update Orders set Saved = 1",
            transaction: transaction,
            cancellationToken: token));
    await transaction.CommitAsync(token);
}
