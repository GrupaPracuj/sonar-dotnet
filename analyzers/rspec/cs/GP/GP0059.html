An assembly that holds message contracts should not use forbidden ORM, web, transport or other infrastructure types.

Why is this an issue?

Contracts are the one thing several independently deployed services agree on, which is why they are usually packaged on their own and referenced by everybody. The moment a contract assembly uses a type from Entity Framework, ASP.NET Core, MassTransit or another configured infrastructure namespace, every consumer of the contracts inherits that dependency - and inherits the version of it the producer happened to build against. A consumer that only wanted to read a message now has to resolve an ORM.

The rule reports the use of a forbidden type inside a contract assembly rather than the project reference itself, because that points at the code to change instead of at the csproj. It checks member and delegate signatures, method return types, base classes, implemented interfaces and generic type constraints, including forbidden types nested inside generic arguments.

Exceptions

The rule only runs when the assembly's exact name or final name segment matches contractAssemblyNames, which defaults to Contracts - so Contracts and names ending in .Contracts are checked, while ordinary service projects are never reported. forbiddenNamespaces defaults to the ORM, web and transport namespaces; add domain namespaces to it only as an explicit project policy.

How to fix it

Keep contracts on the BCL. Move anything that needs an ORM, a web framework or the bus into the service that owns it, and map to the contract at the boundary.

Code examples

Noncompliant code example

// in MyCompany.Orders.Contracts
public sealed record OrderAccepted(Guid OrderId, JsonPatchDocument Changes); // Noncompliant {{'JsonPatchDocument' comes from 'Microsoft.AspNetCore.JsonPatch', which a contract assembly should not depend on.}}

Compliant solution

// in MyCompany.Orders.Contracts
public sealed record OrderAccepted(Guid OrderId, IReadOnlyList Changes);
