An identifier should use the standard spelling for well-known compound words and terms, as documented in Microsoft's own naming guidelines.

Why is this an issue?

The .NET Framework Design Guidelines maintain a "Capitalizing Compound Words and Common Terms" table that fixes, once and for all, how a specific set of frequently misspelled compound words should be written. A name can follow every casing rule - PascalCase for a type, camelCase for a parameter - and still get one of these words wrong, because casing style and word spelling are two independent concerns. EndPoint is valid PascalCase, but the standard spelling is the single word Endpoint. Filename is valid PascalCase too, but the standard spelling splits it into two words, FileName. Neither mistake is caught by an analyzer that only checks casing style (such as the naming-convention rules driven by dotnet_naming_rule entries), because both wrong spellings are, casing-wise, perfectly fine.

This rule checks identifiers against a small, fixed dictionary taken directly from Microsoft's table - not a general-purpose spell checker - so it only ever fires on one of these specific, well-known terms, and false positives on unrelated words are effectively impossible.

Checked spellings

The complete set of corrections is:

  • Single-word fixes: Cancelled to Canceled, EMail to Email, ID to Id, OK to Ok, PI to Pi, and Writeable to Writable.
  • Words that should be split: Bitflag to BitFlag, Filename to FileName, Username to UserName, and Whitespace to WhiteSpace.
  • Words that should be joined: CallBack to Callback, EndPoint to Endpoint, GridLine to Gridline, HashTable to Hashtable, MetaData to Metadata, MultiPanel to Multipanel, MultiView to Multiview, NameSpace to Namespace, and PlaceHolder to Placeholder.

Exceptions

A method or property is not flagged when its name is not the author's free choice to make: an override of a base member, or a member that implements an interface member (explicitly, or implicitly by matching name and signature) by name, must keep the name it was given. Renaming it would either fail to override the base member, or - for an implicit interface implementation - silently stop implementing the interface. Fields, parameters, enum members, and type names have no such constraint and are always checked.

How to fix it

Rename the identifier to the standard spelling shown in the issue message.

Code examples

Noncompliant code example

public class HttpClientOptions
{
    public string EndPoint { get; set; } // Noncompliant {{Rename 'EndPoint' to 'Endpoint' - that is the standard spelling for this compound word.}}
    public string Filename { get; set; } // Noncompliant {{Rename 'Filename' to 'FileName' - that is the standard spelling for this compound word.}}
    public int OrderID { get; set; } // Noncompliant {{Rename 'OrderID' to 'OrderId' - that is the standard spelling for this compound word.}}
}

Compliant solution

public class HttpClientOptions
{
    public string Endpoint { get; set; }
    public string FileName { get; set; }
    public int OrderId { get; set; }
}
