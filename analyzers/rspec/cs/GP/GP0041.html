A method in a test class that looks like a test but carries no test attribute never runs.

Why is this an issue?

A test that does not run is worse than no test at all. It sits in the file looking like coverage, it passes review, and it keeps passing forever because it is never executed - so the behavior it was written to protect can break without anything turning red. The usual cause is mundane: the attribute was lost in a merge, or a test was copied and the attribute was not carried over.

[TestClass]
public class TokenValidatorTest
{
    [TestMethod]
    public void Accepts_A_Valid_Token() { /* ... */ }

    public void Rejects_An_Expired_Token() { /* ... */ }  // never runs
}

Neither of the two rules nearby catches this. S3433 checks the signature of methods that have a test attribute, so a method without one is invisible to it. S2187 only reports a test class that contains no test case at all, so a class with several real tests and one unannotated method passes. That leaves exactly this case unreported.

Exceptions

Only a class that already contains at least one recognized test is examined, so a plain helper class is never reported. Within such a class the rule reports a public, parameterless, non-static method returning void or Task that carries no attributes at all - a shape that is a test in every framework and is unusual for a helper. A method with any attribute is left alone, which covers the fixture lifecycle ([TestInitialize], [SetUp], [OneTimeTearDown], ...), and so is Dispose, which is how xUnit expresses teardown.

The recognized test attributes, with or without the Attribute suffix, are: MSTest [TestMethod] and [DataTestMethod]; xUnit [Fact] and [Theory]; NUnit [Test], [TestCase] and [TestCaseSource]. Both Dispose and DisposeAsync are excluded as lifecycle methods.

A method that implements an interface member is not reported either: the interface, not an attribute, is what makes the framework call it. That covers xUnit's IAsyncLifetime.InitializeAsync/DisposeAsync and IDisposable.Dispose, as well as a project's own fixture interfaces.

How to fix it

Add the test attribute the rest of the class uses, or - if the method really is a helper - make it private so its intent is unambiguous.

Code examples

Noncompliant code example

[TestClass]
public class TokenValidatorTest
{
    [TestMethod]
    public void Accepts_A_Valid_Token() { /* ... */ }

    public void Rejects_An_Expired_Token() { /* ... */ } // Noncompliant {{Add a test attribute to 'Rejects_An_Expired_Token' or make it private - as it stands it never runs.}}
}

Compliant solution

[TestClass]
public class TokenValidatorTest
{
    [TestMethod]
    public void Accepts_A_Valid_Token() { /* ... */ }

    [TestMethod]
    public void Rejects_An_Expired_Token() { /* ... */ }
}
