Personal data should not be passed in a URL path or query string.

Why is this an issue?

URLs are copied into web server, reverse proxy and CDN logs, stored in browser history, and may be sent to another site in the Referer header. Putting an email address, national identifier, phone number or other personal data in a URL quietly creates additional copies of that data in systems whose retention and access rules are usually broader than those of the application database.

[HttpGet("users/{email}")]
public IActionResult GetByEmail(string email) { /* ... */ }

The rule checks route parameters ({name}) in MVC attributes and Minimal API mappings, and parameters explicitly bound with [FromQuery]. Literal path segments are not checked: /email-addresses is a resource name and carries no caller-supplied value. Arbitrary strings used to build outbound URLs are not analyzed.

The complete, case-insensitive list is email, pesel, phone, iban, surname, firstName, lastName, birthDate, dateOfBirth, creditCard, username and login. Up to three adjacent camel-case, Pascal-case or underscore-separated words are joined before matching.

Exceptions

A trailing Id, Ids, Reference, References, Ref, Count, Length, Uri, Url, Path or Type means the parameter points at, or describes, the data rather than containing it. For example, {emailId}, {birthDateReference} and phoneCount are not reported.

How to fix it

Pass personal data in the request body. When a resource must be addressable, use an opaque identifier that is not personal data on its own.

Code examples

Noncompliant code example

[HttpGet("users/{email}")] // Noncompliant {{URL parameter 'email' looks like it carries personal data - it will end up in server logs, browser history and proxy caches.}}
public IActionResult GetByEmail(string email) { /* ... */ }

Compliant solution

[HttpPost("users/search")]
public IActionResult Find([FromBody] FindUserRequest request) { /* ... */ }
