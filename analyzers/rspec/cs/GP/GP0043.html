The GP architecture policy requires published message types to be declared in a dedicated contract assembly, such as GP.Kaczawa.Contracts.

Why is this an issue?

A message is a contract between independently deployed services. Declaring it inside the producer service makes the producer assembly the source of the wire contract and encourages consumers to depend on service implementation code. A dedicated contracts project gives both sides a small, versionable dependency containing only shared message definitions.

Publishing a type from another assembly is not inherently a runtime failure. This rule enforces the GP assembly-boundary policy so ownership, versioning, and dependencies remain explicit.

How to fix it

Move the message type into the repository's contracts project and publish that type. An assembly named Contracts or ending in .Contracts is accepted by default.

Code examples

Noncompliant code example

// Declared in GP.Kaczawa.Api
public sealed record OrderAccepted(Guid OrderId);

await publisher.Publish(new OrderAccepted(order.Id)); // Noncompliant {{Publish 'OrderAccepted' from a contract assembly; it is declared in 'GP.Kaczawa.Api'.}}

Compliant solution

// Declared in GP.Kaczawa.Contracts
public sealed record OrderAccepted(Guid OrderId);

await publisher.Publish(new OrderAccepted(order.Id));

Exceptions

The comma-separated contractAssemblyNames parameter changes the accepted exact names or final assembly-name segments. Anonymous, dynamic and loose payload shapes remain the responsibility of GP0055 and are not reported twice by this rule. Consumer declarations are outside this rule's scope.
