A database entity or domain object should not be published, sent or consumed as a message.

Why is this an issue?

A message is a contract between two independently deployed services. An entity is an implementation detail of one of them. Using the entity as the message welds the two together: the moment somebody adds a column, renames a property or introduces a navigation property, the wire format of a published message changes - and it changes for every consumer, in a deployment that only touched the producer's database.

The failure is asymmetric and delayed, which is what makes it expensive. The producer's tests pass, the schema migration looks routine, and the breakage surfaces in another team's service, at a time nobody connects to the change that caused it.

Entities also serialize badly. Navigation properties drag half the object graph onto the queue or throw on a lazy-loading proxy, and EF's change tracking metadata is meaningless on the other side.

public class Order            // EF entity, mapped by DbSet<Order>
{
    public int Id { get; set; }
    public Customer Customer { get; set; }
}

await publisher.Publish(order);

A type is treated as an entity when any of the following holds: it appears as the element type of a DbSet<T>, it carries EF mapping attributes ([Table], [Key], [Column], [ForeignKey]), or it derives from one of the base types listed in the entityBaseTypes parameter, or it is declared in one of the namespaces listed in domainNamespaces.

Exceptions

The rule reports the publish, send or consume site rather than the entity, so an entity that is never used as a message is never reported. Both parameters default to empty, which means that out of the box only the two framework-based signals apply - DbSet<T> membership and EF attributes - and the namespace and base-type conventions have to be configured per solution.

How to fix it

Declare a contract type for the message and map the entity onto it at the boundary. The mapping is the seam that lets the schema and the contract change independently.

Code examples

Noncompliant code example

public class Order
{
    [Key]
    public int Id { get; set; }
    public Customer Customer { get; set; }
}

public Task Accept(Order order) =>
    _publisher.Publish(order); // Noncompliant {{'Order' is a database entity - use a dedicated contract type as the message instead.}}

Compliant solution

public sealed record OrderAccepted(Guid OrderId, string CustomerReference, DateTimeOffset OccurredAt);

public Task Accept(Order order) =>
    _publisher.Publish(new OrderAccepted(order.PublicId, order.Customer.Reference, DateTimeOffset.UtcNow));
