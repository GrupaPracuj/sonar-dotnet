The GP architecture policy requires types crossing REST or messaging boundaries to be declared in a dedicated contract assembly, such as GP.Kaczawa.Contracts. Built-in and framework types such as string, int and Guid remain valid without a project-specific contract.

Why is this an issue?

REST requests, REST responses, published messages and sent commands are contracts between independently deployed components. Declaring one inside the service implementation makes that assembly the source of the wire contract and encourages consumers to depend on implementation code. A dedicated contracts project gives both sides a small, versionable dependency containing only shared definitions.

Exchanging a type from another assembly is not inherently a runtime failure. This rule enforces the GP assembly-boundary policy so ownership, versioning and dependencies remain explicit.

How to fix it

Move the request, response, message or command type into the repository's contracts project and use that type at the boundary. An assembly named Contracts or ending in .Contracts is accepted by default.

Code examples

Noncompliant code example

// Declared in GP.Kaczawa.Api
public sealed record CreateOrder(string ProductCode);

[HttpPost]
public ActionResult<Guid> Create(CreateOrder request) => ...; // Noncompliant

Compliant solution

// Declared in GP.Kaczawa.Contracts
public sealed record CreateOrder(string ProductCode);

[HttpPost]
public ActionResult<Guid> Create(CreateOrder request) => ...;

Exceptions

The comma-separated contractAssemblyNames parameter changes the accepted exact names or final assembly-name segments. Types from System and Microsoft, including collections containing only such types, are accepted. Controller request parameters are checked when the controller uses ApiControllerAttribute; an explicit FromBodyAttribute is also checked outside API controllers, while MVC view and form models are ignored. Explicitly service-bound and SwaggerIgnoreAttribute parameters are not request contracts. Unannotated interface and abstract Minimal API parameters are also ignored because the runtime can resolve them from dependency injection and static analysis cannot distinguish them reliably from request payloads. Anonymous, dynamic and loose messaging payloads remain the responsibility of GP0055 and are not reported twice by this rule. Consumer declarations are outside this rule's scope.
