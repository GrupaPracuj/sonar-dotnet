A dictionary lookup that checks ContainsKey before calling Add should use TryAdd instead.

Why is this an issue?

The pattern if (!dict.ContainsKey(key)) dict.Add(key, value); hashes the key and walks the bucket twice: once inside ContainsKey, and again inside Add if the check passes. Dictionary<TKey, TValue>.TryAdd does the same job with a single lookup - it adds the entry and returns true when the key is absent, or does nothing and returns false when it is already present. The two-step version is not just slower; it also invites a subtle race in code that looks single-threaded but is not, since another thread can insert the key in the gap between the check and the add.

if (!cache.ContainsKey(key))
{
    cache.Add(key, value);
}

Exceptions

The rule only fires when the two calls target the exact same expression and the exact same key, the if has no else, and the receiver's type implements IDictionary<TKey, TValue>. The same-looking pattern on List<T>, HashSet<T> or any other ICollection<T> is a different, valid idiom - those types have no TryAdd to fall back to - and is left untouched. A negated check with an else branch is also left alone, since the two branches together carry more meaning than the rewrite could preserve.

How to fix it

Replace the whole if with a single call to TryAdd.

Code examples

Noncompliant code example

if (!cache.ContainsKey(key)) // Noncompliant {{Use 'TryAdd' instead of checking 'ContainsKey' before 'Add' - it does the lookup once instead of twice.}}
{
    cache.Add(key, value);
}

Compliant solution

cache.TryAdd(key, value);
