An exception thrown while performing an access check (HasClaim, IsInRole) should not be silently swallowed.

Why is this an issue?

An access check can fail for reasons other than "access denied" - a misconfigured identity provider, a malformed claim, a downstream call timing out. An empty catch block around that check hides the difference between "the user is not allowed" and "the check itself is broken", and leaves no trace that anything went wrong. MITRE describes the underlying weakness as:

The product detects a specific error, but takes no actions to handle the error.

A broken access check that fails open (falls through to false/denied by accident) is merely inconvenient; one that fails closed in the wrong direction is a real gap that nobody will know to investigate.

try
{
    return user.IsInRole("Admin");
}
catch (InvalidOperationException)
{
}

This rule covers what rule S2486 deliberately leaves alone. S2486 reports an empty catch or catch (Exception) without a filter, on general error-handling grounds; reporting those here as well would only put a second issue on the same line. What remains - an empty catch of a specific exception type, or one behind a when filter - looks deliberate rather than forgotten, which is exactly why it is worth pointing out around an access check.

The rule checks catches around a try block that directly calls HasClaim or IsInRole. Both are resolved semantically - IsInRole has to come from a System.Security.Principal.IPrincipal and HasClaim from System.Security.Claims.ClaimsPrincipal/ClaimsIdentity - so a domain member that merely shares the name does not make the surrounding try an access check. It reports a catch that neither logs the caught exception nor always throws, including a catch that silently returns a fallback value or writes the exception through an unrecognized output API. An empty unfiltered catch or catch (Exception) is left to S2486 to avoid duplicate issues.

How to fix it

At minimum, log the exception in the catch block so the failure is visible instead of silent.

Code examples

Noncompliant code example

public bool HasAccess(User user)
{
    try
    {
        return user.IsInRole("Admin");
    }
    catch (InvalidOperationException) // Noncompliant {{Do not silently swallow an exception around an access check - at least log the failure.}}
    {
    }

    return false;
}

Compliant solution

public bool HasAccess(User user)
{
    try
    {
        return user.IsInRole("Admin");
    }
    catch (InvalidOperationException ex)
    {
        _logger.LogWarning(ex, "Role check failed");
    }

    return false;
}
