Exception messages should not include values whose names indicate secrets or personal data.

Why is this an issue?

Exceptions routinely cross more boundaries than their original author expects. They are logged by global handlers and telemetry libraries, attached to traces, returned by background-job dashboards and sometimes exposed by an API error path. A password, token, email address or national identifier embedded in the message is therefore likely to be copied into systems with different access and retention policies.

throw new InvalidOperationException($"Account {email} failed with token {token}");

The rule analyzes the argument semantically mapped to an exception constructor's message parameter. It checks direct string interpolation, string concatenation and string.Format.

The shared, case-insensitive secret vocabulary is password, pwd, secret, token, apiKey, credential, credentials, privateKey, connectionString, bearer and sessionId. The shared personal-data vocabulary is email, pesel, phone, iban, surname, firstName, lastName, birthDate, dateOfBirth, creditCard, username and login. Up to three adjacent camel-case, Pascal-case or underscore-separated words are joined before matching, so names such as ApiKey, refresh_token and DateOfBirth are recognized.

Both vocabularies are defined once and shared with the GP logging and URL rules; the secret vocabulary is also used for message contracts. A trailing qualifier such as Id, Reference, Name, Count, Length, Uri, Url, Path or Type prevents a secret match because it describes or points to the secret rather than containing it. A CancellationToken or date/time value whose name contains a secret word is excluded. An exception object whose name contains a personal-data word is also excluded because it carries failure details and a stack trace, not that personal-data value.

Literal text is not reported. A message such as \"Authentication token is invalid\" describes the problem without disclosing the token value.

How to fix it

Use a non-sensitive business identifier in the message and keep the sensitive value in the protected data store where it belongs. The exception type and stable error code should carry the machine-readable meaning.

Code examples

Noncompliant code example

throw new InvalidOperationException(
    $"Account {email} is invalid"); // Noncompliant

Compliant solution

throw new InvalidOperationException(
    $"Account {accountId} is invalid");
