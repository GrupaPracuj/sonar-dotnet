A published event should say which business object or process it is about.

Why is this an issue?

An event that carries data but no identifier tells a consumer that something happened without saying to what. That makes it unusable for the things consumers actually do with events: update their own copy of a record, correlate the fact with work already in progress, or decide whether a newer event has superseded an older one. All of those need a stable key, and none of them can use one that only exists inside the producer.

MessageId, CorrelationId, ConversationId, RequestId and InitiatorId do not count. They identify the message, not the thing the message is about: a redelivery produces a different MessageId for the same fact, and republishing through an outbox produces another one again. A consumer keyed on transport identifiers cannot recognise that it has already seen this event, which is precisely the case idempotency depends on.

public sealed record PaymentReceived(decimal Amount, string Currency, DateTimeOffset OccurredAt);

appConfig.Publishes<PaymentReceived>();

A member counts as a business identifier when one of the accepted names matches it and it is not one of the transport metadata names. Two kinds are accepted by default. Surrogate keys: Id, Number, Reference, Code, Key, Guid, Uuid. Natural keys, which a domain event is just as often identified by: Email, EmailAddress, Login, Username, Nip, Pesel, Regon, Vat. The list is configurable through identifierSuffixes.

The match is case-insensitive and is made either against the end of the member name or against a whole word of it, where words are split on Pascal-case boundaries. That accepts CustomerNIP, whose identifier is not at the end in the expected casing, and CodeValue, whose identifier sits in front of a trailing Value. Because whole words are compared rather than substrings, Identity and IdempotencyMarker still contain no Id. The identifier may live inside a nested payload object when that is how the contract is shaped, for example Source.FileId.

Exceptions

Commands, including legacy *Command types dispatched through a publish API, are outside this event rule. Scheduling and forwarding envelopes that carry a nested message are commands as well.

An event with no data members at all is not reported. A marker event such as MaintenanceModeEnabled is about the system rather than about a particular object, so there is no identifier for it to carry - and requiring one would only produce a field nobody fills in.

How to fix it

Add the identifier of the thing the event is about, named after that thing. Where the event is about a process rather than an entity, the process identifier is the right key.

Code examples

Noncompliant code example

public sealed record PaymentReceived(decimal Amount, string Currency, DateTimeOffset OccurredAt);

appConfig.Publishes<PaymentReceived>(); // Noncompliant {{'PaymentReceived' carries no business identifier, so a consumer cannot tell what it is about.}}

Compliant solution

public sealed record PaymentReceived(Guid PaymentId, decimal Amount, string Currency, DateTimeOffset OccurredAt);

appConfig.Publishes<PaymentReceived>();

public sealed record FileSource(Guid FileId);
public sealed record CopyFileToCdn(FileSource Source, string DestinationPath, DateTimeOffset OccurredAt);

appConfig.Publishes<CopyFileToCdn>();
