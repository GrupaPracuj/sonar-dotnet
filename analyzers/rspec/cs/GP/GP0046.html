A GET action should not persist data or publish messages.

Why is this an issue?

GET is a safe method. MDN states the guarantee:

An HTTP method is safe if it doesn't alter the state of the server. In other words, a method is safe if it leads to a read-only operation.

That guarantee is not advice, it is what the rest of the world acts on. Browsers prefetch links, crawlers follow them, proxies and CDNs cache the response, and clients and service meshes retry a failed GET without asking - because by contract there is nothing to undo. A GET that writes to the database or publishes a message therefore runs an unknown number of times, triggered by things that never intended to call it at all. Duplicated rows and duplicated events from "just a read" endpoint are the usual symptom, and the cause is nearly impossible to find from the outside.

[HttpGet("orders/{id}/confirm")]
public async Task<IActionResult> Confirm(int id)
{
    var order = await _orders.FindAsync(id);
    order.Confirm();
    await _context.SaveChangesAsync();
    await _publisher.Publish(new OrderConfirmed(order.PublicId));
    return Ok();
}

The rule reports these EF Core or EF6 persistence calls on a context, set or EF extension type: SaveChanges, SaveChangesAsync, Add, AddAsync, AddRange, AddRangeAsync, Update, UpdateRange, Remove, RemoveRange, ExecuteDelete, ExecuteDeleteAsync, ExecuteUpdate and ExecuteUpdateAsync. It also reports GP.Juno or MassTransit calls to Publish, PublishBatch, Send and RespondAsync. Only calls made directly in an action annotated with [HttpGet] are checked. The same precise calls are checked inside an inline handler registered with the official ASP.NET Core MapGet extension. Registration code, named handlers, nested lambdas, local functions and lookalike mapping APIs are not attributed to the endpoint.

Exceptions

Work reached through a service the action calls is not reported - the rule does not follow the call graph, so it sees only what the action does itself. An issue here is therefore reliable, but its absence is not proof that the endpoint is read-only.

How to fix it

Move the operation to a method that matches what it does - POST for an action, PUT/PATCH for an update, DELETE for a removal - and leave GET to read.

Code examples

Noncompliant code example

[HttpGet("orders/{id}/confirm")]
public async Task<IActionResult> Confirm(int id)
{
    var order = await _orders.FindAsync(id);
    order.Confirm();
    await _context.SaveChangesAsync(); // Noncompliant {{A GET endpoint should not change state - 'SaveChangesAsync' makes this endpoint unsafe to retry, prefetch or cache.}}
    return Ok();
}

Compliant solution

[HttpPost("orders/{id}/confirm")]
public async Task<IActionResult> Confirm(int id)
{
    var order = await _orders.FindAsync(id);
    order.Confirm();
    await _context.SaveChangesAsync();
    return Ok();
}
