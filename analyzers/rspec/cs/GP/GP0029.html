Deserializers that let the incoming payload decide which types to instantiate should not be used.

Why is this an issue?

Most serializers deserialize into a type you name in the code. A few instead read the type names out of the payload itself and instantiate whatever they find there. That hands control over which code runs to whoever wrote the payload. Microsoft's guidance on BinaryFormatter puts it plainly:

As a simpler analogy, assume that calling BinaryFormatter.Deserialize over a payload is the equivalent of interpreting that payload as a standalone executable and launching it.
The BinaryFormatter.Deserialize method is never safe when used with untrusted input.

Microsoft names four more serializers with the same problem:

The preceding serializers all perform unrestricted polymorphic deserialization and are dangerous, just like BinaryFormatter.

This rule reports BinaryFormatter, SoapFormatter, NetDataContractSerializer, LosFormatter and ObjectStateFormatter, plus JsonSerializerSettings.TypeNameHandling set to anything other than None, which turns Json.NET into the same kind of type-driven deserializer. The Json.NET documentation warns:

TypeNameHandling should be used with caution when your application deserializes JSON from an external source. Incoming types should be validated with a custom SerializationBinder when deserializing with a value other than None. 
var formatter = new BinaryFormatter();
var order = (Order)formatter.Deserialize(stream);

The common objection is that a given payload is trusted. Microsoft addresses that directly - the point is that a trust boundary is easy to miss:

In general terms, the intent of serialization is to transmit an object into or out of an app. A threat modeling exercise almost always marks this kind of data transfer as crossing a trust boundary.

For BinaryFormatter specifically there is also no longer a way to keep the code working: starting with .NET 9 the in-box implementation throws on use, and the switches that previously re-enabled it have been removed.

How to fix it

Move to a serializer that deserializes into the type your code asks for. Microsoft lists the safe in-box options as System.Text.Json, XmlSerializer and DataContractSerializer - note that DataContractSerializer is a different type from the unsafe NetDataContractSerializer. For Json.NET, leave TypeNameHandling at None; if polymorphism is genuinely required, restrict the accepted types with a custom SerializationBinder instead of accepting any type named in the payload.

Code examples

Noncompliant code example

public Order Read(Stream stream)
{
    var formatter = new BinaryFormatter(); // Noncompliant {{'BinaryFormatter' lets the payload decide which types to instantiate - use a serializer that deserializes into a known type.}}
    return (Order)formatter.Deserialize(stream);
}

Compliant solution

public Order Read(Stream stream) =>
    JsonSerializer.Deserialize<Order>(stream);

Noncompliant code example

var settings = new JsonSerializerSettings
{
    TypeNameHandling = TypeNameHandling.All // Noncompliant {{'TypeNameHandling.All' lets the payload decide which types to instantiate - use a serializer that deserializes into a known type.}}
};

Compliant solution

var settings = new JsonSerializerSettings
{
    TypeNameHandling = TypeNameHandling.None
};
