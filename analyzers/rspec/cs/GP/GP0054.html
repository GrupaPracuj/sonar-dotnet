A cancellation exception should not be caught and turned into a successful result.

Why is this an issue?

OperationCanceledException is not a failure - it is the answer to a request to stop. Swallowing it and continuing tells the caller the operation completed, when in fact it was abandoned partway through. Everything downstream then acts on a result that was never produced.

Where this hurts most is shutdown. The host signals cancellation, the code catches it, reports success, and the caller proceeds to acknowledge the message, commit the transaction or return 200 OK - so half-finished work is recorded as finished, at exactly the moment nobody is watching because the process is going away. It is also why a graceful shutdown appears to work in testing and loses data in production: the symptom only appears when the cancellation actually fires mid-operation.

try
{
    await _client.Send(request, cancellationToken);
}
catch (OperationCanceledException)
{
    // treated as success
}

The rule reports a catch of OperationCanceledException or TaskCanceledException unless every path through the catch rethrows or throws a cancellation exception.

Exceptions

A catch that rethrows on every path - with throw;, throw ex; or another cancellation exception - is not reported. Returning, breaking out of a loop, or throwing an unrelated exception does suppress the signal, and logging alone does not count: a log line does not stop the caller from treating the operation as complete.

The rule also stays silent where the exception is not a caller's cancellation in the first place:

  • a when filter that lets the exception through only when nobody asked to stop - catch (TaskCanceledException) when (!cancellationToken.IsCancellationRequested), the documented way to tell an HttpClient timeout apart from a cancellation - or one that explicitly handles the opposite case, when (token.IsCancellationRequested)
  • a timeout the method owns itself: a TaskCanceledException in a method with no CancellationToken parameter, or a token from a local CancellationTokenSource created with a timeout
  • a graceful shutdown boundary: BackgroundService.ExecuteAsync, IHostedService.StopAsync, a loop controlled by !token.IsCancellationRequested, or a PeriodicTimer helper ending on its own timer token
  • an await foreach in a method that takes no cancellation token and returns no result - there is no caller expecting data that could be silently replaced by success

How to fix it

Let the exception propagate. If it has to be handled locally - to clean up, or to record that the work stopped - rethrow afterwards so the caller still learns the operation did not finish.

Code examples

Noncompliant code example

try
{
    await _client.Send(request, cancellationToken);
}
catch (OperationCanceledException) // Noncompliant {{Do not turn cancellation into success - let 'OperationCanceledException' propagate or rethrow it.}}
{
    _logger.LogInformation("Cancelled");
}

Compliant solution

try
{
    await _client.Send(request, cancellationToken);
}
catch (OperationCanceledException)
{
    _logger.LogInformation("Cancelled");
    throw;
}
