A cancellation exception should not be caught and turned into a successful result.

Why is this an issue?

OperationCanceledException is not a failure - it is the answer to a request to stop. Swallowing it and continuing tells the caller the operation completed, when in fact it was abandoned partway through. Everything downstream then acts on a result that was never produced.

Where this hurts most is shutdown. The host signals cancellation, the code catches it, reports success, and the caller proceeds to acknowledge the message, commit the transaction or return 200 OK - so half-finished work is recorded as finished, at exactly the moment nobody is watching because the process is going away. It is also why a graceful shutdown appears to work in testing and loses data in production: the symptom only appears when the cancellation actually fires mid-operation.

try
{
    await _client.Send(request, cancellationToken);
}
catch (OperationCanceledException)
{
    // treated as success
}

The rule reports a catch of OperationCanceledException or TaskCanceledException unless every path through the catch rethrows or throws a cancellation exception.

Exceptions

A block that rethrows - with throw; or throw ex; - or throws another cancellation exception on every path is not reported. Returning, breaking out of a loop, or throwing an unrelated exception suppresses the cancellation signal. Logging alone does not count: a log line does not stop the caller from treating the operation as complete.

A when filter that guarantees cancellation was not requested - catch (TaskCanceledException) when (!cancellationToken.IsCancellationRequested), the documented way to tell an HttpClient timeout apart from a caller's cancellation - is not reported: the filter only lets the exception through when nobody asked to stop, so handling it there hides no cancellation signal.

"Guarantees" is read through the filter's boolean structure, not by looking for the negation anywhere in it. In A && B it is enough that one side guarantees it; in A || B both sides must, because either one can be what let the exception through. So when (!token.IsCancellationRequested && isTimeout) is not reported, while when (!token.IsCancellationRequested || retryTimeouts) is - that filter also accepts a real cancellation. Any filter whose structure the rule cannot read this way leaves the signal suppressed and is still reported.

A TaskCanceledException caught in a method with no CancellationToken parameter is treated as a timeout rather than a suppressed caller signal. Graceful shutdown at a BackgroundService.ExecuteAsync boundary, a catch inside a loop controlled by !token.IsCancellationRequested, and an explicit when (token.IsCancellationRequested) handler are also not reported.

How to fix it

Let the exception propagate. If it has to be handled locally - to clean up, or to record that the work stopped - rethrow afterwards so the caller still learns the operation did not finish.

Code examples

Noncompliant code example

try
{
    await _client.Send(request, cancellationToken);
}
catch (OperationCanceledException) // Noncompliant {{Do not turn cancellation into success - let 'OperationCanceledException' propagate or rethrow it.}}
{
    _logger.LogInformation("Cancelled");
}

Compliant solution

try
{
    await _client.Send(request, cancellationToken);
}
catch (OperationCanceledException)
{
    _logger.LogInformation("Cancelled");
    throw;
}
