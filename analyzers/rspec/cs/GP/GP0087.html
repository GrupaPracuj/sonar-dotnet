A value typed as IEnumerable<T> or IQueryable<T> should not be enumerated more than once.

Why is this an issue?

A local variable or parameter declared as the interface IEnumerable<T> or IQueryable<T> - as opposed to an already-materialized collection such as List<T> or an array - may represent a lazy, re-executable pipeline: a LINQ query, a yield-based iterator, or, worst of all, an Entity Framework Core IQueryable<T> that sends an actual SQL query to the database every single time it is enumerated.

Enumerating such a value a second time - a second foreach, or a LINQ terminal call such as .ToList(), .Count() or .Any() after an earlier enumeration - does not reuse the results of the first pass. It silently re-runs the whole pipeline from scratch. If the underlying source has side effects, reads from something that changes between calls, or is simply expensive, the second enumeration can return different data, run side effects twice, or double the number of round-trips to the database - and none of this is visible at the call site.

IEnumerable<Order> PendingOrders(DbContext db) =>
    db.Orders.Where(o => o.Status == OrderStatus.Pending);

void Process(DbContext db)
{
    var orders = PendingOrders(db);
    foreach (var order in orders)
    {
        Console.WriteLine(order.Id);
    }

    var total = orders.Sum(o => o.Amount); // runs the query against the database again
}

The rule only tracks local variables and parameters whose declared type is exactly the IEnumerable<T> or IQueryable<T> interface. A variable declared as List<T>, an array, or any other concrete collection type is not flagged, even though it also implements IEnumerable<T>: once materialized, repeated enumeration is safe and cheap, so the declared type is what actually tells you whether re-enumerating is a concern.

Enumerations in opposite branches of the same if/else, in different sections of the same switch statement, or in different arms of the same switch expression are treated as mutually exclusive and do not by themselves produce a finding. A switch's governing expression always runs, so an enumeration there is not exclusive with anything, and a switch statement containing goto case or goto default in its own sections gives that exclusivity up entirely - control really can pass through two sections in one execution. Such a goto inside a nested switch only concerns that nested switch and changes nothing here. The rule otherwise uses local syntactic evidence rather than attempting to prove the concrete runtime source or every possible control-flow path, so it is classified as a maintainability/performance code smell rather than a guaranteed runtime bug.

How to fix it

If the value is needed more than once, materialize it a single time - typically with .ToList() or .ToArray() - and reuse the materialized collection for every subsequent enumeration. Which one to use depends on how the result is used afterwards, so this rule does not offer an automatic fix.

Code examples

Noncompliant code example

void Process(IEnumerable<int> source)
{
    foreach (var x in source)
    {
        Console.WriteLine(x);
    }

    var total = source.Sum(); // Noncompliant {{'source' is an unmaterialized sequence and is enumerated more than once here - each enumeration re-runs the underlying query/iterator. Materialize it once with '.ToList()' if you need to use it multiple times.}}
}

Compliant solution

void Process(IEnumerable<int> source)
{
    var materialized = source.ToList();
    foreach (var x in materialized)
    {
        Console.WriteLine(x);
    }

    var total = materialized.Sum();
}
