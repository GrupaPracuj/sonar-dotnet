A controller should use application abstractions rather than depend directly on infrastructure types.

Why is this an issue?

A controller belongs to the layer that handles HTTP: bind the request, call something, turn the result into a response. Microsoft's layering guidance draws the line explicitly:

The UI layer shouldn't make any requests to the DAL directly, nor should it interact with persistence directly through other means.

The same guidance places DbContext squarely on the far side of that line, listing "EF Core types (DbContext, Migration)" among Infrastructure types, alongside repositories - and states for the UI layer:

No direct instantiation of or static calls to the Infrastructure layer types should be allowed in the UI layer.

When a controller queries the context itself, the query becomes part of the endpoint. A second endpoint that needs the same data gets its own copy, and the two drift apart - one remembers the IsDeleted filter or the Include, the other does not. Testing the endpoint now means standing up a context, so the logic worth testing is reachable only through a database. And a change to the model has to be chased through every controller that happened to query it.

[ApiController]
public class OrdersController : ControllerBase
{
    private readonly ShopDbContext _context;

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id) =>
        Ok(await _context.Orders.FirstOrDefaultAsync(x => x.Id == id));
}

This rule reports a DbContext, database connection, HttpClient, IDbExecute or ITransactional implementation reaching a controller as a field, constructor parameter or local variable. Types are resolved semantically; names such as OrderService are not used as evidence.

In an assembly whose name ends with .Api, the rule also reports persistence operations and direct DbContext/DbConnection dependencies in non-controller runtime types. DI registration such as AddDbContext<T> remains allowed because registering an implementation is a composition-root responsibility.

How to fix it

Move the query behind a service or repository that the controller depends on through an interface, and let the controller call that. The query then lives in one place, can be tested without a database, and the controller is left with the HTTP concerns that are actually its job.

Code examples

Noncompliant code example

[ApiController]
public class OrdersController : ControllerBase
{
    private readonly ShopDbContext _context; // Noncompliant {{Do not use infrastructure type 'ShopDbContext' directly in a controller - depend on an application abstraction instead.}}

    public OrdersController(ShopDbContext context) =>
        _context = context;

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id) =>
        Ok(await _context.Orders.FirstOrDefaultAsync(x => x.Id == id));
}

Compliant solution

[ApiController]
public class OrdersController : ControllerBase
{
    private readonly IOrderRepository _orders;

    public OrdersController(IOrderRepository orders) =>
        _orders = orders;

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id) =>
        Ok(await _orders.FindAsync(id));
}
