Transport code - a controller, or any runtime type in an *.Api assembly - should depend on application abstractions rather than on infrastructure types directly.

Why is this an issue?

A controller belongs to the layer that handles HTTP: bind the request, call something, turn the result into a response. Microsoft's layering guidance draws the line explicitly:

The UI layer shouldn't make any requests to the DAL directly, nor should it interact with persistence directly through other means.

The same guidance places DbContext squarely on the far side of that line, listing "EF Core types (DbContext, Migration)" among Infrastructure types, alongside repositories - and states for the UI layer:

No direct instantiation of or static calls to the Infrastructure layer types should be allowed in the UI layer.

When a controller queries the context itself, the query becomes part of the endpoint. A second endpoint that needs the same data gets its own copy, and the two drift apart - one remembers the IsDeleted filter or the Include, the other does not. Testing the endpoint now means standing up a context, so the logic worth testing is reachable only through a database. And a change to the model has to be chased through every controller that happened to query it.

What counts as an infrastructure type

In a controller, all of these:

  • DbContext - EF Core's Microsoft.EntityFrameworkCore.DbContext or EF6's System.Data.Entity.DbContext, and anything deriving from either
  • DbConnection - System.Data.Common.DbConnection and anything deriving from it, such as SqlConnection
  • HttpClient
  • a type implementing Juno's IDbExecute or ITransactional

In a non-controller type inside an assembly whose name ends with .Api, the list is narrower: only DbContext and DbConnection. Declaring a persistence operation there - a class implementing Juno's IDbExecute - is a placement question this rule does not answer; an architecture test or the absence of a data access package reference in the API project is a better guard.

Types are resolved semantically. A name such as OrderService is never used as evidence, and a wrapper around DbContext is not reported for its name alone.

Where the rule looks

The three ways infrastructure reaches transport code: a field, a constructor parameter - including a primary constructor - or a local variable. Action method parameters are excluded, because model binding is a separate concern. A type appearing only as a type argument is not a declaration either, so DI registration such as services.AddDbContext<ShopDbContext>() is left alone: wiring an implementation up is the composition root's job.

How to fix it

Move the query behind a service or repository that the controller depends on through an interface, and let the controller call that. The query then lives in one place, can be tested without a database, and the controller is left with the HTTP concerns that are actually its job.

Code examples

Noncompliant code example

[ApiController]
public class OrdersController : ControllerBase
{
    private readonly ShopDbContext _context; // Noncompliant: a DbContext reaching a controller as a field

    public OrdersController(ShopDbContext context) =>
        _context = context;

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id) =>
        Ok(await _context.Orders.FirstOrDefaultAsync(x => x.Id == id));
}

Compliant solution

[ApiController]
public class OrdersController : ControllerBase
{
    private readonly IOrderRepository _orders;

    public OrdersController(IOrderRepository orders) =>
        _orders = orders;

    [HttpGet("{id}")]
    public async Task<IActionResult> Get(int id) =>
        Ok(await _orders.FindAsync(id));
}
