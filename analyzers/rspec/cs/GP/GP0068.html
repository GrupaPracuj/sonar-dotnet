Under the GP compatibility convention, an enum a contract puts on the wire should have a zero value meaning "not recognised".

Why is this an issue?

Enums on a contract are the part most likely to grow. A new status, a new reason, a new category - the producer adds a member and deploys, and every consumer that was built before that moment may receive a value it has no name for. What happens next depends on the wire representation, serializer configuration, and consumer logic.

Microsoft's enum guidance names the risk directly:

There is a potential application compatibility problem when the newly added value is returned from an existing API, because poorly written applications might not handle the new value correctly.

Zero is the CLR default for an enum. It is therefore the natural fallback when a field is absent or otherwise left at its default value. Giving zero an explicit name such as Unknown lets consumers recognize that default instead of silently interpreting it as a real business state.

An unknown wire value does not automatically become zero. A numeric value may deserialize as an unnamed enum value, while an unknown string may be rejected or handled differently depending on the serializer, converter, and options. The zero member is a compatibility convention for missing/defaulted data; consumers still need an explicit strategy for values their serializer does not recognize.

public enum OrderStatus
{
    Pending,     // = 0, so a missing/defaulted status becomes "Pending"
    Accepted,
    Shipped,
}

The rule only looks at enums a contract actually exposes, so an internal enum is not reported. The accepted names come from unknownValueNames, which defaults to Unknown,Unspecified,None - Microsoft's guidance suggests None for the zero value generally, while an integration contract is usually clearer with Unknown, since the point is that the field has no recognized business value rather than a valid state.

How to fix it

Add a zero member named for the unknown case and shift the real values up. On an enum that is already published, keep the existing numbers and give zero its name only if zero was never a valid value - otherwise renumbering is itself a breaking change.

Code examples

Noncompliant code example

public enum OrderStatus // Noncompliant {{'OrderStatus' is exposed by a contract but has no zero value named Unknown - a consumer cannot represent a value it does not recognise.}}
{
    Pending = 1,
    Accepted = 2,
}

public sealed record OrderAcceptedContract(Guid OrderId, OrderStatus Status);

Compliant solution

public enum OrderStatus
{
    Unknown = 0,
    Pending = 1,
    Accepted = 2,
}

public sealed record OrderAcceptedContract(Guid OrderId, OrderStatus Status);
