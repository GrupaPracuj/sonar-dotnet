Contracts should not expose enums.

Why is this an issue?

Producers and consumers of a contract are deployed independently. Adding an enum member is source-compatible for the producer, but an older consumer does not know its meaning. Depending on the serializer and representation, the consumer may receive an unnamed numeric value, reject an unknown string, or silently take a fallback path that was never intended for the new state.

A zero member named Unknown or None, explicit numeric assignments, and string serialization each address only part of this problem. None gives an older consumer the semantics of a value introduced after it was built. The GP convention therefore avoids enums at service boundaries altogether.

Only enums actually exposed by a contract are reported. Internal domain enums remain valid.

What is considered a contract?

The rule does not infer contracts from type names. It follows enums exposed by source types declared in a Contracts or *.Contracts namespace, actual ASP.NET controller or Minimal API response payloads, and types published, sent, responded with or registered through GP.Juno or MassTransit. Declarations from referenced projects are not reported.

How to fix it

Expose a stable primitive representation, typically a documented string, and translate it to the domain enum inside each service. Consumers can then handle unknown values explicitly without depending on the producer's enum definition.

Code examples

Noncompliant code example

public enum OrderStatus // Noncompliant {{'OrderStatus' is exposed by a contract. Do not use enums in contracts because producers and consumers evolve independently.}}
{
    Unknown = 0,
    Pending = 1,
    Accepted = 2,
}

public sealed record OrderAcceptedContract(Guid OrderId, OrderStatus Status);

Compliant solution

public sealed record OrderAcceptedContract(Guid OrderId, string Status);
