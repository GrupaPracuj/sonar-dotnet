Message contracts (events and commands) should be plain data carriers and must not contain business behavior.

Why is this an issue?

A message contract describes what happened (an event) or what should happen (a command); it is serialized, transported and deserialized by the messaging infrastructure, often by a different service or a different version of the same service than the one that produced it. When a message class also carries methods with business logic, that logic silently becomes part of the wire contract:

public class NotifyUser
{
    public string Email { get; set; }

    public void SendNow() { /* ... calls an email service directly ... */ }
}
  • Consumers may call the method expecting it to behave the same way it did on the producer side, even though the two sides can evolve independently.
  • The behavior is not visible in the serialized payload, so it is easy to forget it exists when the contract is changed.
  • It blurs the boundary between the messaging layer and the domain layer, making the contract harder to reason about and to version.

Keeping message contracts free of behavior forces business logic to live where it belongs - in the handler that receives the message - and keeps the contract itself a stable, predictable data shape.

Only methods the author added are treated as behavior. Mutable properties and fields are not flagged, and neither are members that describe the value rather than act on it: overrides, explicit interface implementations, Equals/GetHashCode/ToString/ Deconstruct/Clone, and everything a record declaration generates for you. A static method that returns an instance of the contract itself is a factory - it constructs the message rather than acting on it - and is not flagged either.

The issue is reported at the point where the contract is registered for publishing or sending, not on the contract's own declaration - the declaration usually lives in a different file, often a different project, than the registration.

How to fix it

Move any behavior out of the message class and into the component that handles the message. The message class itself should only expose the data needed to describe the event or command.

Code examples

Noncompliant code example

public class NotifyUser
{
    public string Email { get; set; }

    public void SendNow() { /* ... calls an email service directly ... */ }
}

appConfig.Sends<NotifyUser>(); // Noncompliant {{Message contract 'NotifyUser' should not contain business behavior.}}

Compliant solution

public class NotifyUser
{
    public string Email { get; set; }
}

public class NotifyUserHandler
{
    public void Handle(NotifyUser message) { /* ... calls an email service directly ... */ }
}

appConfig.Sends<NotifyUser>();
