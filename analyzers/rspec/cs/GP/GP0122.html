A SQL Server string column referenced by an index or primary key should have a bounded length.

Why is this an issue?

FluentMigrator's AsString(int.MaxValue) and AsString(-1) create NVARCHAR(MAX). SQL Server does not allow a MAX column as an index key, so a migration that indexes such a column fails when deployed.

The rule correlates FluentMigrator column and index expressions by constant schema, table and column name, across the whole migration history of the project - a column is normally declared in one migration and indexed in a later one. The column can come from WithColumn, AddColumn or AlterColumn, and the index from a separate Create.Index, from PrimaryKey() or from Indexed() on the column chain.

A column that any migration declares with a bounded length is never reported, on the grounds that bounding it is exactly how this defect gets fixed and migration order cannot be recovered from the source. Unindexed MAX columns, computed names and lookalike APIs are ignored as well.

How to fix it

Choose the smallest length that covers the identifier or value domain.

Noncompliant code example

Create.Table("Sessions")
    .WithColumn("WalletId")
    .AsString(int.MaxValue); // Noncompliant
Create.Index("IX_Sessions_WalletId")
    .OnTable("Sessions")
    .OnColumn("WalletId");

Compliant solution

Create.Table("Sessions")
    .WithColumn("WalletId")
    .AsString(256);
Create.Index("IX_Sessions_WalletId")
    .OnTable("Sessions")
    .OnColumn("WalletId");
