Diagnostics that expose application data or detailed database errors should only be enabled in development.

Why is this an issue?

Entity Framework Core sensitive-data logging includes values from queries and entity properties in diagnostic messages. Detailed errors add database-level context to exceptions. The database developer page renders migration and database failure details for interactive debugging. These features are useful locally, but in a shared or production environment they can expose personal data, credentials, schema information and query values through logs or error pages.

options.EnableSensitiveDataLogging();
services.AddDatabaseDeveloperPageExceptionFilter();

For this rule, sensitive information is not a fixed list of identifier names. It means the runtime data and implementation details exposed by these framework features: query parameter values, entity property values, connection or provider error details, database and schema names, SQL and migration details, and any personal data or credentials contained in those values. Consequently, the rule recognizes the diagnostic API being enabled rather than trying to infer the contents of every value that the application may process.

The rule checks EF Core EnableSensitiveDataLogging() and EnableDetailedErrors() when enabled with no argument or with the constant value true, and ASP.NET Core AddDatabaseDeveloperPageExceptionFilter(). A call is accepted when the enclosing method performs the framework's IsDevelopment() check or when it is inside the conventional StartupDevelopment class. Runtime boolean configuration is not reported because the analyzer cannot prove that it enables the feature outside development.

The official Sonar rule S4507 already covers UseDeveloperExceptionPage(); this rule deliberately does not duplicate it.

How to fix it

Enable the diagnostic only in a development-specific branch. Keep production diagnostics limited to identifiers and error information that is safe to retain.

Code examples

Noncompliant code example

options.EnableSensitiveDataLogging(); // Noncompliant

Compliant solution

if (environment.IsDevelopment())
{
    options.EnableSensitiveDataLogging();
}
