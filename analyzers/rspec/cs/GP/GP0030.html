A value that arrives as a parameter of a controller action should be passed to the logger as an argument, not interpolated or concatenated into the message template.

Why is this an issue?

When request input is interpolated into the message, whatever the caller sent becomes part of the log line itself rather than a value carried alongside it. MITRE describes the weakness as:

The product constructs a log message from external input, but it does not neutralize or incorrectly neutralizes special elements when the message is written to a log file.

The practical consequence depends on what reads the logs. A caller who sends a value containing newlines can append lines that look like genuine log entries, so a plain-text log or anything grepping it can be made to show events that never happened - which is exactly what someone covering their tracks wants. Where logs are shipped onward, the injected text is also read by whatever parses them next.

Interpolation loses the structure as well. With a constant template the placeholder name and the value are recorded separately, so the value stays a queryable field; interpolating it flattens both into one string and the template stops being stable across calls, which is what log aggregation groups on:

[HttpGet]
public IActionResult Search(string query)
{
    _logger.LogInformation($"Searching for {query}");
    return Ok();
}

The general form of this mistake - any non-constant log template - is already covered by the built-in .NET analyzer rule CA2254, enabled by default as a suggestion in .NET 10, on observability grounds. This rule deliberately reports only the narrower security-relevant case: the interpolated value is a parameter of the enclosing controller action, so it comes from the route, the query string or the body. It does not follow a value through local variables or fields.

How to fix it

Keep the template constant and pass the value as an argument. Microsoft's logging guidance explains why this is more than a style preference:

The arguments themselves are passed to the logging system, not just the formatted message template. This enables logging providers to store the parameter values as fields.

Code examples

Noncompliant code example

[HttpGet]
public IActionResult Search(string query)
{
    _logger.LogInformation($"Searching for {query}"); // Noncompliant {{Pass 'query' as a logging argument instead of interpolating it into the message template - it comes straight from the request.}}
    return Ok();
}

Compliant solution

[HttpGet]
public IActionResult Search(string query)
{
    _logger.LogInformation("Searching for {Query}", query);
    return Ok();
}
