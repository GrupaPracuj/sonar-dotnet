A wire contract (a request/response DTO, or a message contract) should not declare a property of a type that doesn't survive JSON serialization.

Why is this an issue?

System.Text.Json and Newtonsoft.Json can only serialize data. A Stream, a Task, a delegate or an IntPtr describes a runtime operation or a process-local handle; an Exception, a Type, a CancellationToken, an IServiceProvider, a ClaimsPrincipal, an HttpContext, a DbContext or a DataTable is a live object belonging to the current process and request. None of them means anything on the other side of an HTTP call or a message queue. Depending on the serializer and the exact type, this either throws at serialization time or silently produces an empty object - both cases are usually discovered much later than when the property was added, once something on the receiving end unexpectedly gets a missing or malformed field.

public class UploadRequest
{
    public Stream File { get; set; }
}

The rule checks properties, public fields, and positional members (record and record struct primary constructor parameters) of classes, records, and record structs whose own name ends with Dto, Request, Response, Contract, Event, Command or Message. It does not trace whether a type is actually reachable from a controller action or a message declaration - it goes by name alone, so a contract named differently is not checked.

Base classes are walked, so a type deriving from Exception or from DbContext is reported too - those are almost always used through a derived type.

The complete banned-type list is System.IO.Stream, Task (including Task<T>), IntPtr, UIntPtr, Exception and derived exceptions, Type, Delegate and custom delegates, CancellationToken, IServiceProvider, ClaimsPrincipal, DataTable, DataSet, HttpContext, and DbContext from either Entity Framework Core or Entity Framework 6.

Public fields are included because the two serializers disagree about them: Newtonsoft.Json serializes public fields, while System.Text.Json ignores fields unless configured otherwise. A non-serializable field therefore either behaves like the property case or silently disappears depending on which serializer the endpoint happens to use - neither is a contract worth shipping. static and const fields are skipped, since they are not part of the serialized instance.

How to fix it

Remove the property from the contract. If the underlying data is genuinely needed on the other side, expose it as a value (for example the file's bytes, or a completion flag) instead of the runtime object that produced it.

Code examples

Noncompliant code example

public class UploadRequest
{
    public Stream File { get; set; } // Noncompliant {{'File' has type 'System.IO.Stream', which does not serialize to JSON meaningfully - remove it from this contract.}}
}

Compliant solution

public class UploadRequest
{
    public byte[] FileContent { get; set; }
    public string FileName { get; set; }
}
