Why is this an issue?

When a query cuts the result set - TOP (1), OFFSET/FETCH NEXT - the ORDER BY stops being cosmetic and becomes the definition of which rows are returned. SQL Server is only obliged to honour the ordering you asked for; among rows that compare equal it may return them in any order, and that order can change with the query plan, the index chosen, statistics or parallelism.

Ordering only by a timestamp is the usual way this goes wrong. Timestamps look unique, and in testing they are: rows are created seconds apart, so ties never appear. In production - a batch insert, a bulk import, a GETUTCDATE() default shared by rows written in the same statement - they do.

For TOP (1) the effect is that an arbitrary one of the tied rows wins. For paging it is worse: with no total order, a row can be returned on two consecutive pages, or skipped entirely, because the boundary between page n and page n+1 falls inside a group of tied rows and the engine is free to arrange that group differently for each query.

What is the potential impact?

Rows are silently skipped or processed twice while paging, and single-row lookups return a different row than the one intended - intermittently, and typically only under production data volumes.

Exceptions

Only ordering terms that are plain column references are considered. A query ordered by an expression - a CASE, a function call - is left alone, even though it has the same problem, because whether the expression is unique cannot be judged from the text.

How to fix it

Append a column that is unique within the table - typically the primary key - as the last ordering term. That leaves the intended ordering untouched and makes the sort a total order, so the result no longer depends on the plan.

Noncompliant code example

private const string Sql = """
                           SELECT c.ExternalSystemId, c.ExternalCvId
                           FROM dbo.ExtractionOrders c
                           WHERE c.ExtractionVersion = @CurrentVersion
                           ORDER BY c.CreatedDateUtc
                           OFFSET @OffsetSize ROWS
                           FETCH NEXT @PageSize ROWS ONLY;
                           """; // Noncompliant: rows sharing CreatedDateUtc can be paged over twice, or missed

Compliant solution

private const string Sql = """
                           SELECT c.ExternalSystemId, c.ExternalCvId
                           FROM dbo.ExtractionOrders c
                           WHERE c.ExtractionVersion = @CurrentVersion
                           ORDER BY c.CreatedDateUtc, c.ExtractionOrderId
                           OFFSET @OffsetSize ROWS
                           FETCH NEXT @PageSize ROWS ONLY;
                           """;
