A database call should not be made inside a for, foreach, while or do loop.

Why is this an issue?

Executing a query or command once per loop iteration - the classic "N+1" pattern - turns what could be a single round-trip to the database into N of them. Each round-trip pays for network latency and connection/command overhead on top of the query itself, so the total cost scales linearly with the size of whatever collection the loop is iterating over. Code that looks fine against a handful of test rows can become the slowest part of a request once it runs against a real dataset, and it puts avoidable load on the database.

async Task UpdateStock(IDbConnection connection, IEnumerable<(int ProductId, int Quantity)> changes)
{
    foreach (var change in changes)
    {
        await connection.ExecuteAsync(
            "UPDATE Products SET Stock = Stock - @Quantity WHERE Id = @ProductId", change); // one round-trip per item
    }
}

How to fix it

Send every row in a single command instead of one command per item: pass the whole collection as a table-valued parameter or a single UPDATE ... FROM/bulk statement, or - with Dapper - pass the collection directly to Execute, which sends it as one batched command rather than issuing it once per element in a loop written by hand.

Code examples

Noncompliant code example

async Task UpdateStock(IDbConnection connection, IEnumerable<(int ProductId, int Quantity)> changes)
{
    foreach (var change in changes)
    {
        await connection.ExecuteAsync( // Noncompliant {{This database call runs once per loop iteration - batch the calls or move it outside the loop.}}
            "UPDATE Products SET Stock = Stock - @Quantity WHERE Id = @ProductId", change);
    }
}

Compliant solution

async Task UpdateStock(IDbConnection connection, IEnumerable<(int ProductId, int Quantity)> changes) =>
    // Dapper sends the whole collection as one batched command instead of one round-trip per item.
    await connection.ExecuteAsync("UPDATE Products SET Stock = Stock - @Quantity WHERE Id = @ProductId", changes);

Exceptions

Only a call that executes directly and synchronously inside the loop body is reported. A call made from a nested lambda, local function, or LINQ query clause - even one invoked from within the loop - is not reported, since it may run once, be deferred, or run on a different schedule than the loop itself.

The rule is intentionally limited to IDbConnection/IDbCommand/IDbTransaction execute methods (which also covers Dapper, since its Query/Execute methods are extension methods on those interfaces) and to DbContext.SaveChanges/SaveChangesAsync. It does not flag an Entity Framework LINQ query (context.Set<T>().FirstOrDefault(...) and similar) executed inside a loop, since telling such a query apart from an equally common and legitimate lookup on an already-small, filtered sequence would require more context than a purely syntactic check can reliably obtain.

This rule does not distinguish a genuine per-item call from a bounded retry loop that repeats the same call after a failure. Such a loop still makes a database call once per iteration, so it is reported like any other; if it is a deliberate retry, treat the finding as a false positive rather than restructuring it.
