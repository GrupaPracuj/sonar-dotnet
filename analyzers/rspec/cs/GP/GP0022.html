A value whose name suggests it holds personal data (an email address, a national ID number, a phone number, ...) should not be passed to a logging call.

Why is this an issue?

Logs typically live far longer than the request that produced them, get shipped to third-party aggregation services, and are read by a wider group of people than the data subject ever agreed to. Writing personal data into logs quietly turns a diagnostic tool into an additional store of personal data that has to be inventoried, retained and protected like any other - it just usually isn't.

_logger.LogInformation("New user registered with {Email}", email);

Only calls to Microsoft.Extensions.Logging.ILogger (LogTrace/LogDebug/LogInformation/ LogWarning/LogError/LogCritical) and Serilog (Log.* / ILogger.*) are checked. For each argument, only its own name - or, for the message template, the name of each {Placeholder} - is inspected; the rule does not know whether logging this particular field is actually required for audit purposes in your context.

How to fix it

Log an identifier that isn't personal data on its own (for example a user ID) instead of the personal data itself, or mask/truncate the value if some of it is genuinely needed for support.

Code examples

Noncompliant code example

_logger.LogInformation("New user registered with {Email}", email); // Noncompliant {{Do not log 'Email' - its name suggests it holds personal data.}}

Compliant solution

_logger.LogInformation("New user registered with id {UserId}", userId);
