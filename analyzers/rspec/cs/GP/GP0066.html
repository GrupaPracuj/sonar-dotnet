A message contract should not double as a database entity.

Why is this an issue?

A contract is an agreement with other services about a wire format. A table is a private storage decision that nobody outside the service is entitled to see. Mapping one type to both makes it answer to two owners who change it for unrelated reasons and on different schedules.

It is arguably worse in this direction, because the contract is the shared artefact. A column added for local storage - an Id, an IsProcessed flag, a RowVersion - becomes part of the published payload for every consumer, and a migration cannot be applied without changing what other services receive. Conversely, a consumer's request to rename a field turns into a database migration.

The shapes also pull apart in practice. A contract wants immutable members and no surrogate key; an entity wants a key, change tracking and navigation properties. Making one type satisfy both ends with a type that is bad at each.

public sealed record OrderAcceptedContract(Guid OrderId, DateTimeOffset OccurredAt);

public class ShopDbContext : DbContext
{
    public DbSet<OrderAcceptedContract> AcceptedOrders { get; set; }  // now also a table
}

The rule reports a source contract appearing as the element of a DbSet<T>, configured through modelBuilder.Entity<T>(), or carrying EF mapping attributes. A type is a contract when it is declared in a Contracts or *.Contracts namespace, is an actual ASP.NET controller or Minimal API response payload, or is published, sent, responded with or registered through GP.Juno or MassTransit. Type names and suffixes are not evidence.

Exceptions

An outbox or inbox table that stores messages is a legitimate case of persisting a contract - but it stores the serialized payload alongside its own columns rather than mapping the contract type itself, so it does not match this shape.

How to fix it

Declare a separate entity for storage and map between the two. Where the intent is an outbox, store the serialized message in a column of a table you own.

Code examples

Noncompliant code example

public class ShopDbContext : DbContext
{
    public DbSet<OrderAcceptedContract> AcceptedOrders { get; set; } // Noncompliant {{'OrderAcceptedContract' is a message contract - persisting it makes the wire format and the schema the same thing.}}
}

Compliant solution

public class AcceptedOrderRecord
{
    public int Id { get; set; }
    public Guid OrderId { get; set; }
    public DateTimeOffset OccurredAt { get; set; }
}

public class ShopDbContext : DbContext
{
    public DbSet<AcceptedOrderRecord> AcceptedOrders { get; set; }
}
