A using declaration or statement should not construct its resource with an object initializer whose member assignments can throw.

Why is this an issue?

using var x = new Foo { A = Expr1(), B = Expr2() }; looks like a single atomic step, but it is not. The object is constructed first, then each member assignment inside the { } block runs, one after another, and only once every one of them has completed does the whole expression's result get assigned to x. The using only starts tracking the resource for disposal at that final assignment.

If any member assignment inside the initializer throws, the already-constructed instance is discarded without ever being assigned to x. Since using never got to see it, Dispose() is never called - a resource leak that only happens on the exception path and is completely invisible when the happy path is tested.

using var connection = new SqlConnection { ConnectionString = BuildConnectionString() }; // if BuildConnectionString() throws, the SqlConnection just created is leaked

How to fix it

Construct the resource first, with no initializer, so the using starts tracking it for disposal immediately. Assign every member in separate statements afterwards - if one of them throws, the using still disposes the already-bound instance.

Code examples

Noncompliant code example

using var connection = new SqlConnection { ConnectionString = BuildConnectionString() }; // Noncompliant {{This 'using' constructs 'connection' via an object initializer - if a member assignment throws, the instance is never bound and 'Dispose' is never called. Assign the risky members in separate statements after construction.}}

Compliant solution

using var connection = new SqlConnection();
connection.ConnectionString = BuildConnectionString();

Exceptions

An initializer is reported when an assigned value carries a realistic risk of throwing, or when an assignment invokes a property setter that is not provably a source auto-property setter. Assignments of literals or bare identifier/parameter references to fields and source auto-properties are not reported. Setters from referenced assemblies and explicit setter bodies remain in scope because their behavior cannot be proven harmless.
