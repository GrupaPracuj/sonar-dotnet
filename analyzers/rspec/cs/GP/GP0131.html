When a returned ProblemDetails sets Status, it should carry the same status the response itself returns.

Why is this an issue?

The status now appears twice: once in the HTTP status line and once inside the body. When the two disagree, the response answers the same question in two different ways and there is nothing to say which one is authoritative. A client branching on the transport status takes one path, a client reading ProblemDetails.Status takes another, and the same error is handled inconsistently across consumers. Proxies, gateways and logs follow the status line, so the body's value is the one that quietly goes unnoticed.

RFC 9457 makes this normative. The status member is advisory and exists for the consumer's convenience, but "Generators MUST use the same status code in the actual HTTP response, to assure that generic HTTP software that does not understand this format still behaves correctly". A mismatch also defeats the one diagnostic use the RFC grants consumers: reading status to recover the code the generator originally produced, in case an intermediary or cache has changed it since.

The rule compares the two only when Status is set to a compile-time constant in the object initializer of a returned ProblemDetails, and when the response factory selects a known status. A value assigned dynamically is not guessed at, and a ProblemDetails that leaves Status unset is fine - the framework fills it in from the response.

How to fix it

Set Status to the status the response returns, or leave it unset and let the framework supply it.

Code examples

Noncompliant code example

return BadRequest(new ProblemDetails { Status = StatusCodes.Status422UnprocessableEntity }); // Noncompliant: the response returns 400

Compliant solution

return BadRequest(new ProblemDetails { Status = StatusCodes.Status400BadRequest });

Leaving it out is equally correct:

return BadRequest(new ProblemDetails { Title = "The order is invalid" });
