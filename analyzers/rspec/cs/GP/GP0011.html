A response returned from a permission check should use 403 (Forbid), and a response returned from an authentication check should use 401 (Unauthorized).

Why is this an issue?

RFC 9110, the current HTTP semantics standard, defines the two status codes precisely:

401 (Unauthorized) status code indicates that the request has not been applied because it lacks valid authentication credentials for the target resource.
403 (Forbidden) status code indicates that the server understood the request but refuses to fulfill it.

In practice: a 401 response means the caller's identity could not be established or its credentials were rejected - the client's reasonable reaction is to (re-)authenticate. A 403 response means the caller is known, but isn't allowed to perform the requested operation - re-authenticating won't help; the client needs different permissions. The rule looks for two mirror-image mistakes:

A permission/role check (IsInRole(...), HasClaim(...)) that returns 401 instead of 403 - the caller's identity is not in question here, only whether their role/claims allow the operation, so 401 wrongly suggests that logging in again would help:

if (!User.IsInRole("Admin"))
{
    return Unauthorized(); // should be Forbid() - the caller is authenticated, just not an Admin
}

An authentication check (Identity.IsAuthenticated) that returns 403 instead of 401 - there is no established identity yet to be "forbidden", so 403 wrongly suggests that the caller is known and simply denied:

if (!User.Identity.IsAuthenticated)
{
    return Forbid(); // should be Unauthorized() - there is no caller identity yet
}

Either way, the response code tells the client the wrong thing to do next.

Exceptions

A condition that mixes both kinds of checks, or neither (for example !IsAuthenticated || !IsInRole(...)), is intentionally left alone rather than guessed at.

How to fix it

Return Forbid() from a permission check and Unauthorized() from an authentication check.

Code examples

Noncompliant code example

public IActionResult DeleteUser()
{
    if (!User.IsInRole("Admin"))
    {
        return Unauthorized(); // Noncompliant {{This looks like a permission check; return 403 (Forbid) instead of 401 (Unauthorized).}}
    }

    return Ok();
}

Compliant solution

public IActionResult DeleteUser()
{
    if (!User.IsInRole("Admin"))
    {
        return Forbid();
    }

    return Ok();
}

The same mismatch also happens in the other direction, for an authentication check:

Noncompliant code example

public IActionResult DeleteUser()
{
    if (!User.Identity.IsAuthenticated)
    {
        return Forbid(); // Noncompliant {{This looks like an authentication check; return 401 (Unauthorized) instead of 403 (Forbid).}}
    }

    return Ok();
}

Compliant solution

public IActionResult DeleteUser()
{
    if (!User.Identity.IsAuthenticated)
    {
        return Unauthorized();
    }

    return Ok();
}
