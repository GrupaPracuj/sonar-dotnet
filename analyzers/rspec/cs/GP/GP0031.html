A redirect target that arrives as a parameter of a controller action or an inline Minimal API handler should be checked to be local before it is used.

Why is this an issue?

Microsoft's ASP.NET Core guidance describes the problem and the reason it works:

A web app that redirects to a URL that's specified via the request such as the querystring or form data can potentially be tampered with to redirect users to an external, malicious URL. This tampering is called an open redirection attack.

What makes it effective is that the link the user inspects is yours. They see your host name at the start of the URL, trust it, and click; the redirect then delivers them to a copy of your login page on someone else's host. Microsoft's own example walks through the result: the user logs in again on the fake site, believing their first attempt simply failed, and:

The user most likely remains unaware that their credentials are compromised. 
public IActionResult LogOn(string returnUrl)
{
    // ...
    return Redirect(returnUrl);
}

This rule reports a parameter of the enclosing controller action passed to Redirect or RedirectPermanent when that parameter can still decide the destination. It also covers the official Microsoft.AspNetCore.Http.Results.Redirect and TypedResults.Redirect factories inside inline handlers registered with the framework MapGet, MapPost, MapPut, MapPatch, MapDelete, or MapMethods methods. A parameter appended to a path that is already fixed in the code, such as Redirect("/orders/" + id), cannot leave the site and is not reported. A single slash is not enough: Results.Redirect("/" + destination) can form a protocol-relative URL and is reported.

Minimal APIs do not expose the MVC IUrlHelper.IsLocalUrl check. The analysis therefore does not guess that a custom method named IsLocalUrl or another arbitrary helper is safe. Prefer a fixed local destination, or validate dynamic destinations with an explicit, reviewed allowlist before they reach the redirect expression.

The analysis does not follow values through local variables, fields, named handlers, nested lambdas, local functions, or other methods, and it does not treat endpoint registration arguments as handler input.

How to fix it

Microsoft states the requirement as:

Whenever your application logic redirects to a specified URL, you must verify that the redirection URL hasn't been tampered with.

The simplest way is LocalRedirect, which does the check for you - "LocalRedirect will throw an exception if a non-local URL is specified. Otherwise, it behaves just like the Redirect method." Where you need to handle a non-local URL yourself rather than throw, test it first with Url.IsLocalUrl and fall back to a known destination.

Code examples

Noncompliant code example

public IActionResult LogOn(string returnUrl)
{
    return Redirect(returnUrl); // Noncompliant {{Do not redirect to a URL taken from parameter 'returnUrl' - use LocalRedirect or check it with Url.IsLocalUrl first.}}
}

Minimal API:

app.MapGet("/login", (string returnUrl) =>
    Results.Redirect(returnUrl)); // Noncompliant

Compliant solution

public IActionResult LogOn(string returnUrl)
{
    return LocalRedirect(returnUrl);
}

Or, to choose the fallback destination yourself instead of throwing:

public IActionResult LogOn(string returnUrl)
{
    if (Url.IsLocalUrl(returnUrl))
    {
        return Redirect(returnUrl);
    }

    return RedirectToAction(nameof(HomeController.Index), "Home");
}

For an inline Minimal API handler, redirect to a fixed local destination after rejecting a value that is not on a strict allowlist:

app.MapGet("/login", (string returnUrl) =>
    AllowedRedirects.TryGetValue(returnUrl, out var localPath)
        ? Results.Redirect(localPath)
        : Results.Redirect("/"));

The LocalRedirect code fix applies only to MVC controller redirects; it is not offered for Minimal API result factories.
