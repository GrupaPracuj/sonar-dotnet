A call to another service should pass along the CancellationToken that is already available in the calling method.

Why is this an issue?

In a system made of many services calling each other, a call that cannot be cancelled keeps running - and keeps its thread, connection and any locks it holds - for as long as the callee takes to respond, even after the original caller has given up (the client disconnected, an upstream timeout fired, the whole request was cancelled). Under normal conditions this is invisible; under partial failure, when one downstream service gets slow, it is exactly how a local slowdown turns into resource exhaustion in every service upstream of it. A CancellationToken is how .NET propagates "the caller no longer needs this" down the call chain - it is only useful if every link in the chain actually passes it on.

public Task<OrderDto> GetOrder(string id, CancellationToken cancellationToken) =>
    _httpClient.GetFromJsonAsync<OrderDto>($"/orders/{id}");

Exceptions

Only the immediately enclosing method's own parameters are considered "available" - a token reachable only through a field, a captured variable, or an outer method is not. A call that already passes some CancellationToken (even a different one, such as CancellationToken.None) is not flagged, since that is a conscious choice already visible at the call site.

How to fix it

Pass the method's own CancellationToken parameter to the outgoing call.

Code examples

Noncompliant code example

public Task<OrderDto> GetOrder(string id, CancellationToken cancellationToken) =>
    _httpClient.GetFromJsonAsync<OrderDto>($"/orders/{id}"); // Noncompliant {{Pass the available CancellationToken to this call to another service, so it can be cancelled or time out.}}

Compliant solution

public Task<OrderDto> GetOrder(string id, CancellationToken cancellationToken) =>
    _httpClient.GetFromJsonAsync<OrderDto>($"/orders/{id}", cancellationToken);
