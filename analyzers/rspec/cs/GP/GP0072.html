A contract member should be declared with a concrete type, unless polymorphic serialization is explicitly configured.

Why is this an issue?

A serializer reading a payload has to decide what object to create. Given an interface or an abstract class it cannot: there is nothing in the JSON that says which implementation was on the other side. What happens next is worse than an error, because usually there is no error. Microsoft's documentation on System.Text.Json describes the default:

While round-tripping of the payload as WeatherForecastBase is supported, it won't materialize as a runtime type of WeatherForecastWithCity. Instead, it will materialize as a runtime type of WeatherForecastBase.

So the producer serializes a derived object, the consumer deserializes the base one, and every field the derived type added is gone - with no exception anywhere. The condition for it working is explicit:

To enable polymorphic deserialization, you must specify a type discriminator for the derived class.

Even with discriminators configured, a derived type nobody declared throws: "Undeclared types will result in a runtime exception." Either way, the shape has to be a deliberate decision, written down on the type - not an accident of declaring the member as an interface.

What is considered a contract?

The rule does not infer contracts from type names. It checks source types declared in a Contracts or *.Contracts namespace, actual ASP.NET controller or Minimal API response payloads, and types published, sent, responded with or registered through GP.Juno or MassTransit. Declarations from referenced projects are not reported.

public sealed class OrderAcceptedContract
{
    public IPaymentMethod Payment { get; init; }     // which implementation?
    public PricingStrategy Pricing { get; init; }    // abstract
}

Exceptions

Standard materialized collection interfaces are not reported: ICollection<T>, IList<T>, ISet<T>, IDictionary<TKey, TValue> and their read-only counterparts. A deserializer knows what to create for these, so the ambiguity this rule is about does not arise. The lazy sequence interfaces - IEnumerable<T>, IQueryable<T>, IAsyncEnumerable<T> - are not reported here either: a member that defers execution is a separate defect with a separate fix. Additional interfaces can be allowed through the allowedInterfaces parameter.

A type carrying polymorphic configuration - [JsonDerivedType], [JsonPolymorphic], [JsonConverter] or [KnownType] - is not reported: the decision has been made and written down.

How to fix it

Declare the concrete type the contract actually carries. Where the payload genuinely varies, either flatten the variants into one type with a discriminating enum, or configure polymorphism explicitly with [JsonDerivedType] and a stable discriminator string that both sides agree on.

Code examples

Noncompliant code example

public sealed class OrderAcceptedContract
{
    public IPaymentMethod Payment { get; init; } // Noncompliant {{'Payment' is declared as the interface 'IPaymentMethod', so a consumer cannot tell what to deserialize it into.}}
}

Compliant solution

public sealed class OrderAcceptedContract
{
    public PaymentMethodContract Payment { get; init; }
}

public sealed class PaymentMethodContract
{
    public PaymentKind Kind { get; init; }
    public string Reference { get; init; }
}
