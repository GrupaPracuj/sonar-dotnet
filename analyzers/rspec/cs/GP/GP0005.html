GP authorization code should avoid negating a claim-existence check such as !user.HasClaim(...).

Why is this an issue?

HasClaim(...) (and its GP.Juno equivalents, e.g. HasUserClaim()) answers the question "does this claim exist?". Negating that call to decide whether access is granted mixes the existence check with the access decision in a single condition that reads awkwardly ("if the claim does NOT exist, then ...") and is easy to get backwards during a review or a later edit. Making the positive check the basis of the decision keeps the intent explicit: check what is required, then branch on the result.

This is a GP readability and review convention, not evidence of an authorization bypass. Denying access when a required claim is absent is a standard pattern, and ASP.NET Core policy-based or resource-based authorization may express that decision differently. This rule only asks GP code to make the positive requirement explicit.

if (!user.HasClaim("filestore_access"))
{
    return Forbid();
}

How to fix it

Invert the condition so the access decision reads from the positive existence check.

Code examples

Noncompliant code example

public IActionResult DeleteFile(User user)
{
    if (!user.HasClaim("filestore_access")) // Noncompliant
    {
        return Forbid();
    }

    return Ok();
}

Compliant solution

public IActionResult DeleteFile(User user)
{
    if (user.HasClaim("filestore_access"))
    {
        return Ok();
    }

    return Forbid();
}
