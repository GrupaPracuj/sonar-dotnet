A message contract should carry a reference to binary content, not the bytes themselves.

Why is this an issue?

A broker is not a file store. Microsoft's Claim-Check guidance states the problem plainly:

Traditional messaging systems are optimized to manage a high volume of small messages and often have restrictions on the message size they can handle. Large messages not only risk exceeding these limits but can also degrade the performance of the entire system when the messaging system stores them.

Bytes on a message are held in memory by the broker, written to its disk, replicated to every subscriber's queue, and copied again into the error queue if a consumer fails - so a single 5 MB attachment sent to four consumers is not 5 MB of traffic, it is tens of megabytes of broker storage plus the same again on every redelivery. Transports also cap message size, and the failure arrives as a rejected publish long after the contract was designed.

The knock-on effects are worse than the volume. Large messages slow down every other message behind them in the queue, redelivery re-transfers the whole payload to retry work that may have failed for an unrelated reason, and the bytes are now duplicated in a system that has no lifecycle policy for them - the broker will not delete them when the document is deleted.

public sealed record DocumentUploadedContract(Guid DocumentId, byte[] FileContent);

Sending a reference instead keeps the message small and puts the content where it can be authorised, cached, streamed and expired independently.

Exceptions

Stream members are not reported here: a stream does not serialize meaningfully at all rather than merely serializing badly, which is a different defect with a different fix. This rule covers byte[], other byte collections, and members whose name says they hold content (FileContent, AttachmentContent, BinaryData, FileBytes).

A small fixed-size byte array is not distinguishable from a large one by type alone, so a checksum or a hash stored as byte[] is reported too. Where that is intended, name it for what it is (Checksum as a string, or ContentHash) or suppress the issue on that member.

How to fix it

Publish an identifier or URI for the content, together with the metadata a consumer needs to decide what to do before fetching it - size, content type and a checksum.

Code examples

Noncompliant code example

public sealed record DocumentUploadedContract(Guid DocumentId, byte[] FileContent); // Noncompliant {{'FileContent' puts binary content on the broker - publish a reference to it instead.}}

Compliant solution

public sealed record DocumentUploadedContract(
    Guid DocumentId,
    Uri ContentUri,
    long SizeBytes,
    string ContentType,
    string Checksum);
