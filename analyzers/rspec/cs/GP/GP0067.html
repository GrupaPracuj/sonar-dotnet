A contract should not be able to reach a domain type through its members, at any depth.

Why is this an issue?

A contract can look entirely clean in its own declaration and still drag the domain onto the wire one level down. A CustomerContract holding a Customer entity publishes that entity, and every consumer now depends on it just as if it had been published directly - the indirection hides the decision without changing its effect.

This is the version of the problem that survives review, because the offending type is not in the file being read. The contract looks deliberate; the coupling is two hops away, in a property whose type name reads like a contract until you check where it is declared.

The consequence is the one integration contracts exist to prevent. Microsoft's guidance is explicit about why:

You do not want to do that for the same reasons that you do not want to share a common domain model across multiple microservices: microservices must be completely autonomous. 
public sealed record OrderAcceptedContract(Guid OrderId, CustomerSummary Customer);

public sealed record CustomerSummary(string Name, Customer Entity);   // Customer is an EF entity

The rule walks the contract's member graph - through single members and collection elements - and reports the member that first introduces a domain type. A type counts as domain on any of these signals: membership of a DbSet<T>, EF mapping attributes, or the configured entityBaseTypes and domainNamespaces.

How to fix it

Replace the domain type with contract-owned data, or with the identifier the consumer needs to fetch it. The mapping belongs at the boundary that publishes the message, not in the contract.

Code examples

Noncompliant code example

public sealed record CustomerSummary(string Name, Customer Entity); // Noncompliant {{'Entity' lets this contract reach the domain type 'Customer'.}}

Compliant solution

public sealed record CustomerSummary(string Name, Guid CustomerId);
