A contract should not carry a copy of the transport's own metadata.

Why is this an issue?

Transport metadata is set and maintained by the transport, and a consumer reads it from the message context. Copying it into the payload creates a second version of the same fact that nothing keeps in sync: on a redelivery the transport's value changes while the payload's stays as it was, and now two fields disagree about the same message. Whichever one a consumer happens to read becomes a coin toss.

It also hides which of the two is authoritative. Code that correlates on the payload copy silently stops working when a message is republished by an outbox or a retry, because the copy was taken before that happened.

public sealed record OrderAccepted(Guid OrderId, Guid MessageId, DateTimeOffset SentTime);

The rule checks these exact, case-sensitive member names: MessageId, ConversationId, CorrelationId, RequestId, InitiatorId, SentTime, SourceAddress, DestinationAddress, ResponseAddress, FaultAddress and HostInfo.

Exceptions

A field with a genuinely separate business meaning is not the same thing as a copy of the metadata - if the value is the identifier of something in the domain, name it after that (OrderId, ProcessId) and the rule will not match it.

How to fix it

Drop the duplicate and read the value from the consume context. Keep in the payload only what the transport does not already carry.

Code examples

Noncompliant code example

public sealed record OrderAccepted(Guid OrderId, Guid MessageId, DateTimeOffset SentTime); // Noncompliant@-0 {{'MessageId' duplicates transport metadata - read it from the consume context instead.}}

Compliant solution

public sealed record OrderAccepted(Guid OrderId, DateTimeOffset OccurredAt);
