A property's setter should not be more accessible than its getter.

Why is this an issue?

A property is meant to look, from the outside, like a controlled view onto a value: whatever a caller is allowed to read, it should be at least as free to write. A setter that is wider than the getter inverts that expectation - code that cannot see the current value can still overwrite it, which is a surprising and easily misused shape. The .NET Framework Design Guidelines call this out directly: don't give a property a setter whose accessibility is broader than its getter's.

The narrower, more common relative - a public getter with a more restricted setter, so only the declaring type (or a derived type) can change the value while everyone can read it - is the encouraged pattern and is not reported by this rule.

public class Order
{
    public string Status { protected get; set; } // anyone can overwrite Status, but only a derived type can read it back
}

Exceptions

Only properties (and indexers) that declare both a getter and a setter are considered - a write-only property with no getter at all is a different, already-covered shape (see Sonar's own S2376).

C# accessibility is a lattice, not a straight line: protected and internal are mutually incomparable, so neither is "wider" than the other. Comparing such a pair is never reported, to avoid a false positive on the common, deliberate practice of splitting access between "same assembly" and "derived type".

How to fix it

Either narrow the setter so it is no more accessible than the getter, or widen the getter to match the setter - whichever reflects the property's actual intended use.

Code examples

Noncompliant code example

public class Order
{
    public string Status { protected get; set; } // Noncompliant {{'Status' has a setter that is more accessible than its getter - narrow the setter or widen the getter.}}
}

Compliant solution

public class Order
{
    public string Status { get; protected set; }
}
