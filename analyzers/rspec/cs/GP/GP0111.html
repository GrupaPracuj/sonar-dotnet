A catch that translates a SQL Server unique-constraint violation should cover only the database operation whose constraint has domain meaning.

Why is this an issue?

SQL Server error numbers 2601 and 2627 identify a uniqueness violation, but not which operation in a broad transaction failed. When one catch wraps multiple commands, a duplicate in any table is translated into the same domain exception. That can misreport an author-link conflict as an already cataloged book and makes later additions to the transaction silently inherit the wrong mapping.

The rule recognizes Microsoft and System SQL Server exceptions, direct number filters and the conventional SqlServerErrors.IsUniqueConstraintViolation helper. It counts only Juno ADO Execute calls made directly in the try block or inside an inline Juno RunInTransaction callback. Indirect helper calls are not inferred.

How to fix it

Move the operation whose unique constraint is translated into a dedicated method and catch the SQL exception immediately around its single Execute call. Leave the remaining transaction operations outside that catch.

Code examples

Noncompliant code example

try
{
    await transactional.RunInTransaction(async transaction =>
    {
        await transaction.Execute(new InsertBookOperation(book));
        await transaction.Execute(new InsertBookAuthorsOperation(book));
    });
}
catch (SqlException exception) when (exception.Number is 2601 or 2627) // Noncompliant
{
    throw new BookAlreadyCatalogedException(book.Isbn, exception);
}

Compliant solution

private static async Task InsertBookAsync(IDbTransaction transaction, CatalogBook book)
{
    try
    {
        await transaction.Execute(new InsertBookOperation(book));
    }
    catch (SqlException exception) when (SqlServerErrors.IsUniqueConstraintViolation(exception))
    {
        throw new BookAlreadyCatalogedException(book.Isbn, exception);
    }
}
