A route parameter should not be named like it carries a secret (a password, an API key, a token, ...).

Why is this an issue?

A value placed in the URL path travels through places a request body doesn't: web server access logs, reverse proxy and CDN logs, browser history, and the Referer header sent to any third-party resource the page subsequently loads. None of those are designed to hold secrets, and none of them get cleaned up when the secret is later rotated. A route parameter named token or apiKey is a strong hint that a value meant to stay confidential is being passed exactly where it is most likely to leak.

[HttpGet("sessions/{token}")]
public IActionResult GetByToken(string token) { /* ... */ }

Only route parameters ({name}) are checked, not literal path segments - a fixed segment like /api-keys is just a resource name, it doesn't carry a caller-supplied value. A name that only points at a secret rather than holding one is not reported either: a trailing Id, Reference, Name, Uri, Path, Type, Count or Length makes {apiKeyId} and {credentialReference} compliant.

How to fix it

Pass the value in the request body, in an Authorization header, or as a short-lived opaque identifier instead of a path segment.

Code examples

Noncompliant code example

[HttpGet("sessions/{token}")] // Noncompliant {{Route parameter 'token' looks like it carries a secret - it will end up in server logs, browser history and proxy caches.}}
public IActionResult GetByToken(string token) { /* ... */ }

Compliant solution

[HttpGet("sessions/current")]
public IActionResult GetCurrent([FromHeader(Name = "Authorization")] string token) { /* ... */ }
