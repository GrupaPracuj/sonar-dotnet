An enum a contract puts on the wire should assign a number to every member.

Why is this an issue?

By default an enum serializes as its underlying number, and without explicit assignments those numbers come from declaration order. That makes the wire format depend on the position of each member in the source file - which is exactly the kind of thing a refactor changes without anyone treating it as a change.

Sorting the members alphabetically, inserting a new one in the middle to keep related values together, or deleting an obsolete one all shift every number after that point. Nothing fails to compile, no test breaks on the producer side, and the meaning of data already published silently changes: a message that said 2 for Shipped is now read as Cancelled. Historical messages in a queue or a replay log are reinterpreted too.

public enum OrderStatus
{
    Pending,      // 0
    Accepted,     // 1 - inserting anything above here renumbers everything below
    Shipped,      // 2
}

Explicit numbers make the wire contract independent of the source layout: members can be reordered, grouped or removed and the numbers stay where they are. Every member has to be explicit, because a single implicit one still moves when its predecessor changes.

Only enums a contract actually exposes are reported - an internal enum can be reordered freely, since nothing outside the assembly reads its numbers.

Exceptions

An enum that is serialized as a string puts no ordinal on the wire, so reordering its members changes nothing there and it is not reported. That is recognized through the converter attribute of either serializer: [JsonConverter(typeof(JsonStringEnumConverter))] (System.Text.Json, including the generic JsonStringEnumConverter<TEnum>) and [JsonConverter(typeof(StringEnumConverter))] (Newtonsoft.Json). Any other converter says nothing about the wire format and does not exempt the enum.

How to fix it

Assign each member its number. On an enum that is already published, assign the numbers it currently has rather than tidy ones, or the fix becomes the breaking change it was meant to prevent.

Code examples

Noncompliant code example

public enum OrderStatus // Noncompliant {{'OrderStatus' is exposed by a contract with implicit values - reordering or inserting a member would silently change what is already on the wire.}}
{
    Unknown,
    Pending,
    Accepted,
}

public sealed record OrderAcceptedContract(Guid OrderId, OrderStatus Status);

Compliant solution

public enum OrderStatus
{
    Unknown = 0,
    Pending = 1,
    Accepted = 2,
}

public sealed record OrderAcceptedContract(Guid OrderId, OrderStatus Status);
