A database transaction should be started with Juno's ITransactional.StartTransaction(...), not by calling BeginTransaction() on a connection.

Why is this an issue?

Juno tracks the current transaction so that everything running underneath it - nested IDbExecute steps, repositories, the SQL Server lock implementation - joins the same transaction instead of quietly opening a second one. A transaction started directly on the connection is not registered with the transaction accessor, so that sharing stops working: code that looks like it participates in your transaction actually runs outside it, and a rollback leaves behind the writes that took the other path.

Starting the transaction through Juno also makes the isolation level an explicit argument rather than a default inherited from the provider.

using var connection = _connectionFactory.CreateConnection();
connection.Open();
using var transaction = connection.BeginTransaction();

Exceptions

An implementation of ITransactional is not reported - that is where BeginTransaction is supposed to be called, since it is the type whose job is to produce the transaction Juno then tracks.

How to fix it

Inject ITransactional and start the transaction through it, passing the isolation level the work actually needs.

Code examples

Noncompliant code example

public async Task Save(Order order)
{
    using var connection = _connectionFactory.CreateConnection();
    connection.Open();
    using var transaction = connection.BeginTransaction(); // Noncompliant {{Start the transaction with Juno's ITransactional instead of calling 'BeginTransaction' on the connection.}}

    await connection.ExecuteAsync("insert into Orders ...", order, transaction);
    transaction.Commit();
}

Compliant solution

public async Task Save(Order order)
{
    using var transaction = await _transactional.StartTransaction(IsolationLevel.ReadCommitted);

    await transaction.Execute(new InsertOrder(order));
    transaction.Commit();
}
