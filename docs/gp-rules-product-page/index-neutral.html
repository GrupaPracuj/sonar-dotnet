GRUPA A

Bezpieczeństwo i dostęp

Reguły pilnują jawnej polityki dostępu i blokują typowe drogi wycieku danych lub przejęcia kontroli nad żądaniem wychodzącym.

Co zyskuje zespółPubliczny endpoint jest publiczny świadomie, sekret nie trafia do logów, a dane użytkownika nie sterują bezpośrednio URL-em wywołania lub przekierowania.
Niejawna autoryzacjaEndpoint bez żadnej deklaracji wygląda tak samo jak endpoint przypadkiem pozostawiony publicznie.
Wycieki do logówNazwa placeholdera lub argumentu może ujawnić token, hasło albo dane osobowe.
SSRF i open redirectURL pochodzący prosto z requestu nie powinien sterować wywołaniem zaufanej usługi.
Fałszywe poczucie ochronyCredentialed CORS z dowolnym originem lub połknięty wyjątek autoryzacji osłabiają zabezpieczenia.
Endpoints should explicitly declare their access policyMVC i Minimal API muszą jawnie wybrać authorization albo anonymous access.
Secret-like values should not be loggedŁączy placeholder z argumentem i uwzględnia typ wartości, żeby ograniczyć false positive.
Personal data should not be loggedWykrywa logowanie nazw wskazujących m.in. email, PESEL, telefon lub IBAN.
Secrets should not be passed in URLsObejmuje sekrety przekazywane w parametrach ścieżki MVC i Minimal API oraz jawnie bindowanym query stringu.
Personal data should not be passed in URLsOgranicza kopiowanie danych osobowych do logów serwerów, historii przeglądarki i nagłówka Referer.
Whole HTTP and authentication objects should not be loggedŻądania, nagłówki, cookies i tożsamość nie trafiają do loggera jako niekontrolowane kontenery danych.
Sensitive diagnostics should only be enabled in developmentDiagnostyka EF Core i strony błędów bazy nie ujawniają danych ani szczegółów schematu poza developmentem.
Sensitive values should not be included in exception messagesSekrety i dane osobowe nie rozchodzą się przez logi, tracing, dashboardy i odpowiedzi błędów.
Outbound requests should not use a URL taken straight from the requestOgranicza SSRF w wywołaniach do innych usług.
Credentialed CORS policies should restrict allowed originsCredentials wymagają jawnie ograniczonej listy originów.
Przykład zastosowania
Problem
app.MapGet("/users/{id}", GetUser);
// Brak jawnej polityki dostępu
Jawna intencja
app.MapGet("/users/{id}", GetUser)
   .RequireAuthorization();
GRUPA B

API i semantyka HTTP

Reguły ujednolicają znaczenie odpowiedzi HTTP i oddzielają modele transportowe od encji oraz szczegółów implementacyjnych.

Co zyskuje zespółKlient nie musi obsługiwać kilku przypadkowych wariantów tej samej operacji, a endpoint nie ujawnia encji, stack trace’a ani nieoczekiwanych efektów ubocznych.
Stabilne kolekcjePusty wynik GET to pusta kolekcja, nie 204 ani 404.
Poprawne statusyCreate zwraca 201, DELETE nie zwraca body, auth rozróżnia 401 i 403.
Czysta granica APIEncje bazy i szczegóły wyjątków nie wychodzą do klienta.
Jednolity format błędówOdpowiedzi błędów korzystają z RFC 9457 ProblemDetails.
GET collection endpoints should not return 204 No ContentPusta kolekcja zachowuje ten sam kształt odpowiedzi.
Resource-creating endpoints should return 201 CreatedSemantyka create jest widoczna w statusie i lokalizacji zasobu.
Endpoints should not return database entitiesKontrakt API nie jest przypadkowo sprzężony ze schematem persystencji.
GET endpoints should not have side effectsGET pozostaje bezpieczny dla retry, cache i automatycznych crawlerów.
Error response bodies should use ProblemDetailsKlienci dostają jeden przewidywalny format błędów.
REST controllers should be declared as API controllersAktywuje przewidywalne zachowania bindingu i walidacji MVC.
Przykład zastosowania
Zmienny kształt odpowiedzi
if (users.Count == 0)
{
    return NoContent();
}
return Ok(users);
Jeden kontrakt kolekcji
if (users.Count == 0)
{
    return Ok(new List<User>());
}
return Ok(users);
GRUPA C

OpenAPI i generowane klienty

Ta grupa porównuje metadane endpointu z tym, co kod rzeczywiście zwraca. Celem jest poprawny protokół, nie tylko ładny Swagger.

Co zyskuje zespółDokumentacja i generowane klienty znają wszystkie odpowiedzi, ich typy oraz scheme security — zanim nieudokumentowana gałąź ujawni się na produkcji.
Brakujące statusyImplementacja zwraca 404, ale metadata opisuje tylko 200.
Martwe deklaracjeDokumentacja obiecuje status sukcesu, którego żadna ścieżka nie zwraca.
Niewłaściwy typ bodyStatus bez body ma zadeklarowany typ albo błąd z body nie ma typu.
Niespójne security schemesId użyte w operacji musi dokładnie pasować do definicji schematu.
Returned HTTP statuses must be declared in ProducesResponseTypeAnalizuje jawne fabryki odpowiedzi i typed results.
HTTP actions should declare their successful response typeKlient zna model odpowiedzi sukcesu.
HTTP error responses with bodies should declare their typeBody błędu jest częścią kontraktu, a nie ukrytym szczegółem.
OpenAPI security scheme identifiers should match exactlyChroni przed dokumentacją deklarującą inne zabezpieczenie niż konfiguracja.
Declared successful HTTP response statuses should be returned by an action pathWykrywa deklaracje, których implementacja nie realizuje.
Przykład zastosowania
Implementacja
[ProducesResponseType(200)]
public IActionResult Get(string id) =>
    Find(id) is { } value
      ? Ok(value)
      : NotFound(); // 404 nieopisane
Kontrakt zgodny z kodem
[ProducesResponseType(200)]
[ProducesResponseType(404)]
public IActionResult Get(string id) =>
    Find(id) is { } value
      ? Ok(value)
      : NotFound();
GRUPA D

Kontrakty i messaging

Reguły oddzielają modele integracyjne od implementacji oraz pilnują, aby komunikaty były wersjonowalne i kompletne.

Co zyskuje zespółProducent i konsument mogą rozwijać się niezależnie, kontrakt ma jawnego właściciela, a infrastruktura transportowa nie przecieka do modelu biznesowego.
Własność kontraktuTypy przekraczające REST lub messaging boundary pochodzą z dedykowanego assembly Contracts.
Ewolucja wartościEnum nie zamyka starszego konsumenta na nowe stany producenta.
Kompletność zdarzeniaEvent niesie czas wystąpienia i biznesowy identyfikator.
Oddzielenie transportuKontrakt nie duplikuje metadata MassTransit ani nie zależy od typów infrastruktury.
API contracts should come from contract assembliesREST request/response i message types mają jawne, wersjonowalne miejsce.
Contracts should not expose enumsNowa wartość producenta nie staje się nieznaną semantyką u starego konsumenta.
Published events should carry the time they occurredEvent odróżnia czas biznesowy od czasu dostarczenia.
Contract collections should be stable when serializedKontrakt nie ujawnia mutowalnych lub nieprzewidywalnych kształtów kolekcji.
Contracts should not duplicate transport metadataMessageId, CorrelationId i SentTime pozostają odpowiedzialnością transportu.
Message dispatch should match its transport registrationPublish/send/request odpowiada sposobowi rejestracji kontraktu.
Przykład zastosowania
Brak czasu biznesowego
public record PaymentReceived(
    Guid PaymentId,
    decimal Amount,
    string Currency);
Czas wystąpienia w kontrakcie
public record PaymentReceived(
    Guid PaymentId,
    decimal Amount,
    string Currency,
    DateTimeOffset OccurredAt);
GRUPA E

Platforma, dane i integracje

Reguły kierują kod przez wspólne abstractions platformowe oraz chronią granice transakcji i propagację cancellation.

Co zyskuje zespółObservability, discovery, konfiguracja, retry i transakcje działają według jednego standardu zamiast zależeć od lokalnej implementacji każdej usługi.
Sieć wewnątrz transakcjiZewnętrzny call przed commit wydłuża locki i może zostawić niespójny efekt uboczny.
Obejście platformyRaw MassTransit, Consul, SmtpClient lub ręczny scheduler omijają wspólne polityki platformowe.
Utracona transakcjaDapper operation musi dostać aktywną transakcję i CancellationToken.
Ukryta konfiguracjaTyped configuration i jednokrotna rejestracja type handlerów ograniczają błędy startowe.
Database transactions should not contain external network calls before commitTransakcja nie obejmuje niekontrolowanego czasu odpowiedzi innej usługi.
Calls to other services should propagate the available CancellationTokenAnulowanie requestu kończy również pracę downstream.
Messages should be published through the approved abstraction, not raw transport APIsWspólna warstwa zachowuje organizacyjne konwencje publikacji.
Service discovery should go through the approved abstraction, not a raw clientDiscovery nie wiąże kodu biznesowego z konkretnym klientem infrastruktury.
Dapper operations should receive the active transactionOperacja uczestniczy w transakcji, którą kod już otworzył.
Dapper operations should pass the caller's CancellationTokenZapytanie można przerwać razem z wywołaniem aplikacyjnym.
Przykład zastosowania
Bez CancellationToken
public Task<OrderDto> GetOrder(
    string id,
    CancellationToken cancellationToken) =>
    _httpClient.GetFromJsonAsync<OrderDto>(
        $"/orders/{id}");
Z przekazanym CancellationToken
public Task<OrderDto> GetOrder(
    string id,
    CancellationToken cancellationToken) =>
    _httpClient.GetFromJsonAsync<OrderDto>(
        $"/orders/{id}", cancellationToken);
GRUPA F

Poprawność runtime i utrzymanie

Ta grupa obejmuje pułapki języka i frameworka, które kompilują się poprawnie, ale mają inne zachowanie niż sugeruje kod.

Co zyskuje zespółMniej błędów zależnych od obciążenia, kolejności wykonania lub wyjątkowej ścieżki — czyli przypadków trudnych do odtworzenia podczas zwykłego review.
WspółbieżnośćNieatomowa aktualizacja volatile, przechwycona zmienna pętli i źle użyte ThreadStatic.
Obsługa wyjątkówStatic constructor, exception filter lub wrapper mogą ukryć przyczynę albo zdestabilizować typ.
Zasoby i cancellationObject initializer w using może wyciec, a połknięte cancellation zmienia sterowanie.
Czas i testowalnośćNazwy dat odpowiadają semantyce, a wstrzyknięty zegar nie jest omijany.
Volatile fields should not be updated non-atomicallyVolatile nie zmienia złożonej operacji read-modify-write w atomową.
'[ThreadStatic]' should not be used on non-static fieldsCLR ignoruje atrybut na polu instancyjnym; kod nie zapewnia izolacji per thread.
A loop should not capture its own mutated control variable in a lambda passed to deferred executionLambda nie używa późniejszej wartości zmiennej zamiast wartości z iteracji.
A 'using' should not initialize its resource via an object initializer that can throwWyjątek w initializerze nie pozostawia już utworzonego zasobu bez Dispose.
Caught exceptions should be preserved when wrapping themNowy wyjątek zachowuje original exception jako InnerException.
Injected clocks should not be bypassed by static clocksKod pozostaje deterministyczny i testowalny.
Przykład zastosowania
Ominięty wstrzyknięty zegar
public class Consumer(TimeProvider timeProvider)
{
    public AuditTrace CreateTrace() =>
        new(DateTimeOffset.UtcNow);
}
Jedno kontrolowane źródło czasu
public class Consumer(TimeProvider timeProvider)
{
    public AuditTrace CreateTrace() =>
        new(timeProvider.GetUtcNow());
}
PRZEKRÓJ NIS2

NIS2 w cyklu wytwarzania

Art. 21 NIS2 wymaga proporcjonalnych środków technicznych, operacyjnych i organizacyjnych. Reguły automatyzują tę część kontroli, którą można jednoznacznie sprawdzić w kodzie C#.

Co zyskuje organizacjaPowtarzalne findings w IDE i CI/CD tworzą techniczny ślad stosowania standardu secure development. Analizator wspiera wybrane środki NIS2, ale nie zastępuje analizy ryzyka, obsługi incydentów, ciągłości działania ani audytu zgodności.
Bezpieczne wytwarzanie i utrzymanieKontrole SSRF, deserializacji, diagnostyki, wyjątków i danych w URL-ach wspierają bezpieczeństwo nabywania, rozwoju i utrzymania systemów z art. 21 ust. 2 lit. e.
Kontrola dostępuJawna polityka endpointów, poprawna obsługa wyjątków autoryzacji, claims i CORS wspierają środki kontroli dostępu z art. 21 ust. 2 lit. i.
Ocena skuteczności zabezpieczeńWersjonowane reguły, findings i quality gate dają powtarzalny mechanizm sprawdzania wybranych zabezpieczeń w każdej zmianie kodu.
Odporność usługPropagacja anulowania, granice transakcji i kontrole współbieżności ograniczają klasy awarii istotne dla ciągłości działania.
Art. 21 ust. 2 lit. e — secure development sprawdzany automatycznieReguły wykrywają konkretne podatne konstrukcje i niebezpieczne ustawienia jeszcze przed wdrożeniem.
Art. 21 ust. 2 lit. i — dostęp deklarowany w kodzieEndpointy i mechanizmy uwierzytelnienia mają jawną, możliwą do przejrzenia politykę.
Art. 21 ust. 2 lit. f — stały pomiar zamiast jednorazowej deklaracjiTen sam zestaw kontroli działa lokalnie, na pull requeście i w quality gate.
GRUPA G

Integracje AI

Cztery precyzyjne reguły pilnują technicznych kontraktów integracji z modelami i agentami bez analizowania treści promptów ani zgadywania intencji biznesowej.

Co zyskuje zespółKontrolowany koszt odpowiedzi, stabilna tożsamość agentów, bezpieczna deserializacja i mniejsze ryzyko ujawnienia treści rozmów w logach.
Nieograniczony kosztKażde rozpoznane wywołanie modelu ma dodatni limit tokenów odpowiedzi.
Niestabilna tożsamość agentaDeterministyczna nazwa utrzymuje spójność wątków, pamięci i telemetrii po restarcie.
Nieufna odpowiedź modeluStrukturalny wynik jest deserializowany do typu z odrzucaniem nieznanych pól.
Wrażliwa treść w logachSurowe wiadomości, odpowiedzi i historia konwersacji nie trafiają bezpośrednio do loggera.
AI model invocations should cap output tokensOgranicza koszt i maksymalny rozmiar pojedynczej odpowiedzi modelu.
ChatClientAgent instances should have a stable nameBlokuje nazwy losowe, zależne od czasu i tworzone automatycznie przez framework.
Structured AI responses should be deserialized safelyWymaga typowanego modelu i restrykcyjnej obsługi nieznanych pól.
Raw AI content should not be loggedLogi zachowują zatwierdzone metadane zamiast pełnej treści rozmowy.
Przykład integracji AI
Nieograniczone wywołanie
await client.GetResponseAsync(prompt);
Kontrolowany limit
var options = new ChatOptions
{
    MaxOutputTokens = 800
};
await client.GetResponseAsync(
    prompt, options);
Kod generowany przez agentów

Dedykowane reguły C# sprawdzają standardy w kodzie wygenerowanym przez agentów LLM.

Skille, instrukcje repozytorium i prompt pomagają agentowi zastosować lokalne konwencje. Agent może jednak pominąć instrukcję lub zastosować ją nieprawidłowo. Podczas analizy statycznej Dedykowane reguły C# sprawdzają gotowy kod i zgłaszają naruszenia zdefiniowanych standardów.

✓
Powtarzalny wynikTa sama wersja kodu i analizatora daje ten sam wynik niezależnie od modelu, promptu i użytych skilli.
✓
Konwencje sprawdzane w kodzieDedykowane reguły C# sprawdzają między innymi autoryzację endpointów, ochronę danych, kontrakty zdarzeń, integracje AI, użycie zatwierdzonych abstrakcji platformowych i przekazywanie CancellationToken.
✓
Wyniki dostępne przez MCP SonarQubeAgent może pobrać lokalizację problemu, opis reguły i wskazówki do poprawienia kodu przed utworzeniem PR-a.
